# UI

The Bauherr UI is the Next.js route group `apps/server/src/app/(app)/`, served at `/`. Payload's REST API stays at `/api`, MCP at `/mcp`; `/admin` redirects to `/settings` unless `BAUHERR_ENABLE_ADMIN=1`.

## Routes

| Path | Page |
|---|---|
| `/login` | email + password (local `payload.login`, not the REST endpoint). When OIDC is configured, "Sign in with …" is the primary button and the password form sits under a "Use password" disclosure (open after a wrong password), see [auth](auth.md) |
| `/` | Tickets overview of the selected Workspace, views by `?view=list\|board\|runs` |
| `/requests` | Requests of the selected Workspace: Intake sessions (embed-widget ones included) newest first, read-only, with the primary "New request" button in the header. Columns Request (a Sent title links to `/requests/[id]`, an own Draft's to `/requests/new?session=<id>`; the `#n` Ticket link stays once sent), Product (only with more than one Product), Status `Draft` (open) or `Sent` (submitted), Updated (relative time); no stage text and no sub-ticket list (the Ticket page shows those); abandoned hidden; no conversation text; newest 100. `/requests/new` starts one |
| `/requests/[id]` | One Request (an Intake session of the Workspace, 404 otherwise): title, Product, Draft/Sent, context and acceptance criteria from the draft, one "Next step" ("Continue draft" for the author's own Draft, else the first Ticket that needs the person, else "Nothing for you to do."), the linked Tickets (`ticketNumbers`) as cards with the plain-language stage (Being looked at, planned, built, reviewed, On staging, Done) and the need, and the merged forge comments of those Tickets (oldest first, tagged `#n`, `bauherr:` marker comments hidden) with a comment box (`RequestComposer`: a Ticket select with several Tickets, then `CommentComposer`). Nothing is stored; loader `loadRequest` in `lib/requests.ts` |
| `/runs` | Runs list, Admin only (others redirect to `/`); `/?view=runs` redirects here. Columns Ticket (title links to the Run), Stage, Status, When (relative, full timestamp in the tooltip); Product filter only with more than one Product |
| `/tickets/<id>` | Ticket page, see below |
| `/runs/<id>` | Run page, Admin tab by `?tab=timeline\|list` (`graph` falls back to `timeline`) |
| `/setup` | First-run setup of the selected Workspace, Admin only (others see "Ask an Admin to finish setup."). A checklist of four steps with the word Done or To do each, computed from existing data (no stored flag), and the body of the first undone step; a reload resumes there, `?step=<id>` revisits an earlier one. 1 `connect`: `ConnectionForm` (kind `github`) then Verify (`verifyConnection` asks the forge who the token belongs to and stores `capabilities.verifiedAt` / `lastError`; Done = a verified GitHub Connection). 2 `product`: name, repository and account in one action, `createProductWithRepo` (Product, repository and ticket source; the Product is deleted again if a later create fails); Done = a Product with a repository and a ticket source. 3 `deploy`: the Staging, Approvals and Production sections of the Product page (`DeploySections`) saved with `saveDeploy`, or "Skip, use defaults" (`skipDeploy`, a save without changes); Done = a staging site is set or the Product was saved at least a second after it was created. 4 `request`: `IntakeChat` for that Product; Done = a Ticket or submitted request of the Product exists. The empty states of `/` and `/requests/new` link here ("Set up your Workspace") while the Workspace has no Product; the page stays reachable afterwards and shows all Done. Loader: `lib/setup.ts` |
| `/knowledge` | Knowledge: documents, search, write-backs, see below |

Pages under `(shell)/` get the top bar and require a session; unauthenticated requests redirect to `/login`. Sign out and Workspace selection are server actions in `lib/actions.ts`. The top bar holds the logo, Requests (badge = the caller's open Drafts with messages), Tickets (needs-you badge), Knowledge (only when the Workspace has a connected Knowledge repo; `/knowledge` stays reachable by URL) and the avatar menu (shadcn `DropdownMenu`): email, the Workspace list (only with more than one Workspace), the Theme row, Settings, Sign out. New request (`IntakeChat`): the Product select appears only with more than one Product; the sent state reads "Request #n sent. We'll ask if anything is unclear."; "Discard" on a draft in "Your drafts" opens a modal (native `<dialog>`, never `window.confirm`) with "Keep draft" and "Discard"; the draft's context sits in a closed "Context" disclosure. "New request" is the primary action in the header of `/requests` (and of its empty state); "Your drafts" on `/requests/new` links back to `/requests` ("Requests").

## Overview

Tabs **List**, **Board**, **Runs** on `/`, plus a Product filter and a "Show done" toggle (`?state=all`, Board only); the Product filter is hidden with one Product or fewer (`?product=<id>`). The chosen tab is stored per user in `bauherren.uiPrefs` (`{ view }`, written by the server action `setView`, which validates the view and merges into the freshly read prefs); `/` without `?view=` redirects to the saved one. Data comes from `lib/overview.ts` (`loadOverview(workspace, all)`: open tickets, plus the newest 200 closed ones when `all`; latest Run per ticket from one query; the newest 100 Runs of the Workspace; Products).

- **List**: "Needs you" first, then one section per stage (`triage, plan, build, review, release, done`); empty sections are omitted and a ticket in "Needs you" is not repeated below. Tickets without a stage label count as `triage`, closed ones as `done`.
- **Epics**: a Ticket with sub-tickets (or just split, stage `parent`) is an epic, never a Board card or Graph node. Every sub-ticket card carries an epic tag (short title, colour from the epic id, links to the epic). The `Epic` select (hidden without epics) narrows Board, Graph and Runs via `?epic=<id>`; `?view=epics` lists open epics in rank order with progress bar, `k/n done` and open sub-tickets per column, expandable to the sub-tickets (`Show done` adds closed epics). The epic's Ticket page shows the same progress and list instead of the stage pipeline; plan approval stays there (`lib/epics.ts`). The selected epic is remembered per user (`uiPrefs`) and restored when Board or Runs open without `?epic=`; `?epic=` (All) clears it.
- **Board**: one column per stage. Cards follow `frontierOrder` (`lib/frontier.ts`), right to left like `executionOrder`: Release, Review, Build, Plan, Triage, then the owner's rank, then number; blocked and leased Tickets last. The Plan, Build, Review and Release headers read `count / limit` (the Workspace's WIP limits; `count` skips epics and Tickets still waiting to enter that column), highlighted at the limit and in the danger colour over it; a column without a limit shows the plain count. A Ticket waiting for a full column carries the status "Waiting" whose tooltip reads "Waiting: Build is full (2/2)" (`tickets.waitingFor`, `waitingText` in `lib/wip-limits.ts`); the Ticket page shows the same text as a notice under the stage pipeline. Open cards are sortable by drag and drop or Alt+ArrowUp/Down on a focused card; a move calls `rankTicketAction`, which writes `tickets.rank` (a base-62 fractional key between the two neighbours, per Workspace, never written to the forge). The small position number on a card shows on hover and focus only. New Tickets from the poller rank after the last of their Workspace. `claim_next` takes work in the same order.
**Board card** (`components/OverviewViews.tsx`, `lib/card-status.ts`): title, one status or the needs-you verb, the epic tag, the Product name, and a muted `#number` (plain text, no forge link). The number and the hover-only position are identifiers and are not counted; the other four are: at most 3 text elements in the default view, 4 when the card needs the owner. The Product name (shown only with more than one Product and no Product filter) takes the last free slot, so it drops out of a card that already has a status and an epic tag. One status per card, first match: needs-you verb (replaces the status), `Working` (latest Run live; the label is always "Working"; the activity word, e.g. "building", leads the tooltip), `Blocked`, `Waiting` (`statusOf`, shared with the Epics view). Detail lives in the tooltip (Blocked and Waiting also as `aria-label`): the activity word for Working, plus stage, Run id, who and heartbeat age for Admins only, `Blocked by #8, #9`, the wait reason, and `@login · waiting <age>` / "no reachable owner" on the needs-you verb. No Run link, stage name, `@user` or heartbeat age is visible without hover; the stripe animation (`data-running`) is the Working marker. Epics are never cards, so cards carry no `k/n done`. The empty Board says "Describe what you want built." with a New request button only when the Workspace has a Product and no filter is active; a Workspace without a Product keeps "Set up your Workspace". The Product select stays visible while `?product` is set.

- **Runs** (`/runs`, Admin): the newest 100 Workspace Runs first (Ticket, stage, status, relative time); a line says so when there are more. The `Epic` select narrows them as on the Board; the Product and Epic selects are each hidden when there is nothing to choose (one Product, no epics).
- **Graph** (`?view=graph`): columns by blocker depth. Order inside a column and in the no-dependency section is `executionOrder` (`lib/frontier.ts`): Release, Review, Build, Plan, Triage, then the rest, inside a stage the owner's rank. The legend and the no-dependency section are collapsed `<details>` ("Legend", "No dependencies (N, K running)", the count of running nodes only when K > 0). The no-dependency section is a wrapping grid of small nodes grouped by stage, one heading per stage; Tickets without an execution stage (done, split) sit behind "Show N more". A Ticket whose latest Run is `running` gets `data-running` on its node and Board card: a marching dashed border (stripe on cards) and the activity word from `activity()` (`lib/format.ts`: building, reviewing, planning, deploying, triaging); `awaiting_session` is not animated. With `prefers-reduced-motion` the border is solid accent and the word stays. The Tickets page refreshes every 10 s (`AutoRefresh`), so the state appears and disappears without a reload.

"Needs you" (`needsYou()` in `lib/needs-you.ts`, first match wins): `Approve plan` (stage `plan`, no `bauherr:approved:plan` label, latest Run is a succeeded plan Run), `Run needs you` (latest Run `needs_human`), `Review MR` (stage `review`), `Run failed` (an addition to D5). A plan Run that is `running`, `queued` or `awaiting_session` is "Plan in progress" and not needs-you; D5 (c): when the plan has unanswered critical decisions it reads `Answer decisions` instead of `Approve plan`. The overview fetches the plan Comment from the forge only for tickets that would say `Approve plan`, at most 20 per load (`DECISIONS_LOOKUPS` in `lib/overview.ts`); beyond that they keep `Approve plan`; the Ticket page is always exact. Lookups use one forge source per Product per load and a 3 s timeout; a slow or unreachable forge degrades to `Approve plan`. The Tickets nav item shows the count over open tickets. The need on a card is shown as the bar's verb (`GATES[need].verb`, e.g. `Accept on staging`, `Re-run build`); sorting and counts still use the need. A card with a notified gate carries `@login · waiting <age>` (from `tickets.gateNotified*`) in the verb's tooltip.

## Ticket page

`/tickets/<id>` (Workspace-scoped, 404 otherwise): decision first. In order: **ActionBar** (see below), title, Product name, the stage pipeline (`components/StagePipeline.tsx`; an epic shows its sub-ticket list instead), one muted history line (`Plan approved · Accepted on staging · Approved for production`, only what is true), the Waiting notice, then the gate's decisive content and nothing else: the plan gate (`Gate`) is one row, "Approves"; the release gate (`ReleaseGate`) is the staging summary and the 60-minute notice plus the required-note "Request changes" form, which is hidden until the bar's link `#changes` targets it (`target:flex`, no JS); the other gates have no content, their sentence is the bar's. Below the gate the **owner chat** (`components/OwnerChat.tsx`, `id="answer"`, shown while a decision row exists; there is no list of decisions). Then ONE closed **Details** disclosure (`components/TicketDetails.tsx`, native `<details>`, the id `details` sits on its content so the bar's "Show details" opens it) holding: forge link, Admin-only Budget, Model tiers and merge commit, decision status, the technical idle sentence ("Nothing to do: build is running (Run #5, scheduler)", Admin-only parts for Admins), Dependencies (Blocked by / Blocks), the round-cap findings, **Plan** (shown without its `## Decisions` block), **Worklog** (markdown without its own `## Worklog` heading; answered rows are in its Decisions section; the worklog Comment is the first match, plan and decisions Comments the latest), Attachments and **Runs** (Admin: Run, Stage, Status, Duration, Evidence; others: Stage linking to the Run, Status, When, Evidence; no Mode, Cost or Run ids for non-Admins). The comment composer follows Details. Markdown is rendered by `lib/markdown.ts` (the D4 implementation: raw HTML escaped, images reduced to alt text, links only http(s)). Plan, worklog and labels are read live from the forge through the Product's ticket source; if it is unreachable the page says so.

Writes are server actions in `lib/actions.ts` over `src/lib/actions.ts` (`approvePlan`, `updateWorklog`, `requestReview`, `postDecisions`), the same functions the MCP tools `approve`, `update_worklog`, `request_review` call. `approvePlan` itself refuses while critical rows are unanswered ("Answer the critical decisions first: D2, …"), so the MCP `approve` tool does too; the UI additionally disables the button. The UI actions pass the selected Workspace id and 404 for a ticket of another Workspace. `postDecisions` runs under an in-process per-ticket mutex (double submit); multi-instance deployments need a DB lock later. Submit buttons disable while pending (`SubmitButton`).

**ActionBar** (`components/ActionBar.tsx`, copy in `lib/gates.ts`): the first element of the Ticket page in every state, `data-testid="action-bar"`. Sticky at the top on desktop, fixed to the bottom of the viewport at 640px and below. Left: one sentence for the current need; right: "Show details" (opens Details), on a release gate "Open staging" (the Product's `stagingUrl`, a text link next to Accept), at most one secondary action ("Request changes" reveals the note form on click) and exactly one primary button whose label is the verb of the step. Without a need it says in plain language who is working or what is awaited ("The factory is working on this.", "Waiting for the staging deploy.", "In review.") and shows no button; the technical sentence is in Details. Overview cards show the same verb.

| Answer decisions | Answer N question(s) (`#answer`, the owner chat) | |

**Expedite** (`expediteAction` over `expedite` in `src/lib/actions.ts`): while a Ticket is open, not yet in `release`, not flagged, and the Workspace has the Expedite lane on, the ActionBar shows an outline "Expedite" button next to the primary action. It puts the `bauherr:expedite` label on the Ticket (and removes Triage's `bauherr:expedite-proposed`); the next poll sets `tickets.expedite`. Triage's proposal is the needs-you "Expedite?" whose primary is the same button. Settings > Workflow has the "Expedite lane" switch (Admin). See `docs/spec/workflow.md` "Expedite lane".

**Staging gate** (backend in `src/lib/actions.ts`, UI follows): a Ticket in `release` whose `releaseState` is `on_staging` shows the staging summary Comment, and the bar links the Product's `stagingUrl` as "Open staging"; the bar's "Accept on staging" calls `acceptStaging`, "Request changes" (note required) calls `requestChanges`. Needs-you reads "Accept on staging" for that state and "Staging not confirmed" for `timed_out`. MCP: `post_staging_summary`, `accept_staging`, `request_changes`. Per-Product `stagingUrl`, deploy mode, webhook URL, required checks, gate owners (GitHub logins notified at human gates, picked from the Members with a GitHub login or added by login; empty = Admins with a GitHub login), release mode and the switch "Ask me before production" (shows the effective state: on and disabled while the workflow forces it) are edited on the Product page `/settings/products/<id>`.

**Approve production** (on by default, or per Product with "Ask me before deploying to production"): after "Accept", the Ticket page shows the bar sentence "Approve the production deploy." (needs-you "Approve production") whose button calls `approveProduction`; after a failed or timed out deploy the bar reads "Production deploy failed" with "Approve again". "Approved for production" joins the history line once the label is set. MCP: `approve_production`. Product settings: "Ask me before deploying to production", production webhook URL, production checks. Bauherr's own Product: `production.yml` builds `ghcr.io/getbauherr/bauherr:edge` from the approved sha and reports `production`. Recipe for another Product's label workflow: trigger `issues: labeled` filtered to `bauherr:approved:production` on issues (not PRs); take the Ticket's merge sha from its merged factory PR (head branch `bauherr/<ticket>-*`, not the workflow's HEAD); deploy it; report a check on that sha with the Checks API after the approval (see `.github/scripts/report-check.sh`).

**Needs you and Cancelled** (`lib/liveness.ts`): a review with `reviewState` `needs_human` (any cause but the round cap) reads `Needs you`, a plan/build/review Ticket whose latest Run of the current stage is `cancelled` reads `Cancelled`. The bar's sentence carries the reason: the first line of the latest `Bauherr needs a human:` Comment, or the Run's `error` (also for `Run failed` and `Run needs you`); the Board and epic lists show it after `Needs you:`. `Back to build` (`backToBuild`, note optional) returns the review to Build on its open MR, or with the note to open a new one; `Back to backlog` (`backToBacklog`) moves the Ticket to Triage. Settings > Workspace > Factory health shows `Dead tickets` (0 is the goal) with links and causes.

**Round cap gate**: a review Ticket with `reviewState` `needs_human` and `reviewRounds` above the cap shows the bar "Round cap reached" with the escalation Comment's findings in Details, "Grant one more round" (primary) and "Stop" (no note) in the bar; needs-you reads "Round cap reached". Backend: `grantReviewRound`, `stopReview`; MCP: `grant_review_round`, `stop_review`.

The gate content holds no primary button; the action lives in the ActionBar.

**WIP limits** (`/settings/workflow`, Admin, first section): four number inputs (Plan, Build, Review, Release) with the current count; empty means no limit, a limit is a whole number of at least 1. Saved with `saveWipLimits` into `workspaces.wipLimits` (field access: Admin only); read on every poll, so no deploy is needed. **Paths that never hold a Build** (same page, per Product): a textarea of path globs, one per line (`products.overlapIgnore`, saved by `saveOverlapIgnore`, Admin only, spaces rejected), and below it the list "Suggested from history" (files changed in at least 25% of the last 100 merged PRs, each with its percentage and an Add button; nothing is applied until Add). A Build held for shared paths shows the chip "Waiting: overlaps #N" like a WIP wait. **Where you are asked** (same page): a table of the four human touch points in flow order (Refine, Approve plan, Accept on staging, Approve production) with When, What you do, Where, On/Off (from `humanGates()`) and How to change. Names live in `GATE_NAMES` (`lib/needs-you.ts`); the ActionBar copy in `lib/gates.ts` reads them from there.

### Decision-sheet format (D6)

Rows come from the plan Comment's `## Decisions` block, one bullet each (continuation lines allowed):

`- **D<n> <title>[, critical | — critical | - critical | (critical)]**. Default: <text>. Alternative: <text>. Alternatives: <text>; <text>.`

The options are the default plus each Alternative(s) item (split at `;` and sentence ends outside parentheses and code); "critical" only counts as a suffix marker of the title (a title that merely contains the word does not block approval). Without `Default:` the default is the first sentence; a row with no alternatives is single-choice (one "Accept the default" radio). Saving posts one Comment `<!-- bauherr:decisions -->` with `D<n>: <answer>` lines (replaced on re-save) and appends `- <date> D<n> <title>: <answer>. By: <email>.` under `**Decisions**` in the worklog Comment (created from the worklog template when missing; unchanged answers are not appended again). The owner answers in one assistant-ui chat (`OwnerChat`, `startOwnerIntake` / `askOwnerIntake` in `lib/actions.ts`, intake session persona `owner`): one open row at a time, critical first; the options are chips (default first, marked recommended), a free-text answer is also accepted, recorded verbatim as one line of at most 500 characters (whitespace collapsed, so it cannot forge another `D<n>:` row) and never rewritten by the model. A fixed chip "Why does this matter?" (or a typed question) makes one cheap-tier model call (Ticket, plan and knowledge as context, no other Ticket or Workspace) that explains and records nothing and then offers a "Use my text as the answer" chip, so the model can never block an answer; without a gateway a question gets a fixed notice. A click on a listed option never calls the model. The composer takes at most 500 characters and closes after the summary. Opening the page again resumes the open session at the live head of the queue. The last answer ends with a one-line summary (`lib/owner-summary.ts`); a Triage hold is released by `postDecisions` as before. The sheet format and Comment markers are unchanged; `postDecisions` also serves the MCP tools. Only rows of the live plan are accepted.

### Fake forge (E2E only)

`BAUHERR_E2E_FAKE_FORGE=1` makes `githubFor` (`src/lib/adapters.ts`) return an in-memory `FakeBackend` (`src/lib/fake-forge.ts`) holding ticket #1 of `acme/web` with a plan (two decisions, one critical) and a worklog, and `fakeOwnerModel` (`lib/intake/fake.ts`) answers the owner chat's model call (a message ending in `?` is an explain request); state lives in the server process only. `seed:e2e` adds the matching Connection and ticket source. Start the server with the variable (`next dev`, or a `BAUHERR_TEST_BUILD=1` build, see below) and run Playwright with `E2E_FAKE_FORGE=1` to enable `e2e/ticket.spec.ts`. Never set it outside tests: `assertFakeAllowed` (`src/lib/fake-guard.ts`, called by `adapters.ts` and `intake/fake.ts` at load) throws when the flag is set with `NODE_ENV=production` unless `next build` ran with `BAUHERR_TEST_BUILD=1`; `next.config.ts` inlines that marker into the bundle, so a runtime env var cannot unlock a production image (the Dockerfile never sets it; `tests/fake-guard.test.ts` pins this).

## Run page

`/runs/<id>` (404 outside the selected Workspace), loaded by `lib/run.ts` (`loadRun(workspace, id, includeSteps)`: Steps, tool calls, session owner and agent key are only loaded for Admins, so tokens, model and cost never reach a non-Admin render). Header `#<ticket> <title>`, status chip, stage. Everyone sees the review verdict and findings, evidence, error, links to the Ticket and the MR, and Re-run stage. Admins also get the tabs **Timeline** and **List** and a collapsed **Details** card; Release lock is Admin only (`releaseRunLock` re-checks). No new tables (D5): data = `runs`, `steps` (by `seq`) and `tool_calls` (linked by `step`). The stage pipeline lives on the Ticket page.

- **Timeline**: one bar per Step from its `startedAt` (else `createdAt`) to the next Step (last: Run end, or now while running), scale start/mid/end; tool calls nested as thin bars, laid out back to back from the Step start by `durationMs` (the recorder stores no call start). Bars span step to next step, not the Step's own `createdAt`/duration (accepted drift).
- **List**: Steps with tokens, start, duration; the tool-call count expands (`<details>`) to name, stored input digest, status.
- **Details** (Admin, collapsed `<details>`): launched by (session owner's email for `session` mode, else "scheduler"), start/end/duration, status, model, tokens, cost with `costSource`. Evidence (rendered with `lib/markdown.ts`), error and the Ticket and MR links (`artifacts.prUrl`) show for everyone.
- **Re-run stage**: shown for `failed` and `needs_human` Runs. The server action `rerunStage` (`lib/actions.ts`) re-checks status and Workspace membership (Admins see all Workspaces), calls `startRunIfNeeded` (a Run already active for the stage is opened instead), records a `human_touches` row `rerun:<stage>` and redirects to the new Run. Two-click confirm via `ConfirmButton`.

## Workspace

`currentWorkspace()` (`lib/session.ts`) returns `{ user, workspace, workspaces }`. Admins see all Workspaces, others those in `tenants`. The choice lives in the cookie `bauherr-ws` (slug); missing or invalid falls back to the first.

## Knowledge

`/knowledge` (main nav, every Bauherr): left a document list per source, headed "Built-in" (core pack, Admin only), "Your Knowledge" (Knowledge repo) or the Product's name (its repo: `README.md` + `docs/**/*.md`, indexed at its default-branch commit as product layer `repo-docs/<path>`; markdown only), right the search hits for `?q=` (same backend as `search_knowledge`) or the document of `?doc=<source>:<path>` rendered with `renderMarkdown` (raw HTML escaped). Documents show their title (`title()` in `lib/knowledge.ts`: first heading, else the file name without `.md`, de-dashed and capitalised); no path, source repo or commit is rendered for anyone (the path stays in the `?doc=` URL). Admin only, enforced in `loadKnowledge(…, { admin })` (`user.role === 'admin'`): the core pack (list, search, documents), the "Write-backs" table (open `bauherr/*` PRs of the Knowledge repo with the merge-gate checks via `mergeChecks`; a forge that does not answer within 3 s shows one line; non-Admins trigger no forge call) and the "Only the built-in documents are available" banner shown without a Knowledge repo. Read-only; editing is a separate page. Loaders: `lib/knowledge.ts`.

## Settings

Routes `/settings/workspace`, `/products` (list: Product, Repository, Setup word, Production approval; `/products/new` adds a Product, its repository and its ticket source in one form: Name, Account (a select; a text line when the Workspace has one Connection), Repository (a select filled from the Connection's forge, read once with a 3 s timeout and no retries, plus "Other..." for a typed `owner/name`; when the forge fails the select is replaced by the typed field and the line "Could not list repositories; type owner/name."), and under Advanced the short name, derived from the name until edited. `createProductWithRepo` creates the Product, the repository and the ticket source in that order and deletes what it created when a later create fails; a taken short name shows "Another Product already uses this short name."; on success it opens `/products/<id>#staging`; with no GitHub or GitLab Connection the page shows "Bauherr needs access to GitHub or GitLab first." with an "Add connection" link; `/products/<id>` is the Product page: setup checklist, numbered sections Repository and tickets, Staging, Approvals (the gate ladder in flow order: Answer questions, Approve the plan, Accept on staging, Ask me before production, then "Everything else runs on its own."; Merge automatically; the number field "Re-run a failed check once", 0 or 1; the picker "Who approves?" with the Members that have a GitHub login and an "Add GitHub login" input), Production (shown while production approval is on: a status callout, the picker "Which check reports the production deploy?" and the closed explainer "How does my pipeline know when to deploy?" with a copyable GitHub Actions workflow that reports the check on the Ticket's merge commit), Release notes, Website widget, one Delete Product section; Advanced fields sit behind a disclosure; one "Save changes" form for sections 2 to 5, a fixed bottom bar on phones; non-Admins see it read-only), `/bauherren` (the edit drawer has a "GitHub login", checked with the forge's `userExists` on the Workspace's first GitHub Connection: "GitHub does not know @x. Check the spelling."), `/api-key`, and for Admins `/connections`, `/audit`, `/workflow` (`/settings` redirects to `/settings/workspace`), with a left sub-nav on desktop and tabs on phones. Entry point: avatar menu "Settings" (non-Admins land on `/settings/api-key`). Nav labels: **General** (`/workspace`), **Products**, **People** (`/bauherren`), and for non-Admins **API key**. Admins get a collapsed **Advanced** group (native `<details>`, open while the path is one of its entries) with Connections, Agent keys (`/api-key`), Audit, Workflow, Runs (`/runs`) and the anchors Factory health, Gateway key, Model tiers, Run mode, Knowledge repo on `/settings/workspace` (`#health`, `#gateway`, `#tiers`, `#run-mode`, `#knowledge`). **Check pickers** (`MultiPick` in `components/SettingsForm.tsx`; `productionChecks`, Advanced `deployChecks` and `gateOwners` still post one comma-joined string, no migration): the check names come from `recentChecks(productId)` (`lib/settings.ts`, Product page and `/setup` only): the default branch's newest 5 commits plus the merge commits of the Product's newest 5 Tickets, at most 10 commits, one `listChecks` each in parallel, 3 s in all, each name listed once per commit and sorted by how often it was seen, then by name ("seen on 4 of 10 recent commits · last: success"). Saved names the forge did not report stay listed, checked, as "not seen recently". Without a ticket source, or when the forge fails or is too slow, the line "Could not read checks from GitHub right now. Type the check name instead." shows and the add input still works; saving is never blocked. **Production status callout** (`productionCallouts` in `lib/product-setup.ts`, recomputed on every render): Off (also shown under the switch), Not ready (no check), Almost ready (none of the checks seen lately), Ready; an unreadable forge counts as Ready. A second callout "No approver" shows when no gate owner and no Admin has a GitHub login.

**Selects and defaults** (`PickField` in `components/SettingsForm.tsx`: a shadcn Select (`ui/select.tsx`, Radix) of the known values plus "Other..." for a typed one, posted under the field's name; without options it is the plain text field, so a failing forge never blocks Save): Workspace model tiers (the preset's models, empty = preset default) and Knowledge repo (`KnowledgeRepo`: Repository listed from the chosen Connection via `listRepos`, re-read when the Connection changes); Connections (GitLab Base URL starts as `https://gitlab.com`, `awsRegion` and `vertexRegion` are selects with the first value preselected); Members (Role defaults to `bauherr`, Workspaces are checkboxes; the SSO subject stays text); New request (`IntakeChat` shows the Product select with more than one Product and preselects the last used, `localStorage` key `bauherr-product`). `e2e/selects.spec.ts` covers each page: with the fake forge the Repository is a combobox, otherwise (forge fails) a text field.

**Admin is part of the product.** Every admin function is a page of this UI in the same design system. `/admin` (Payload) is a developer escape hatch only, off by default: it redirects to `/settings` for everyone until `BAUHERR_ENABLE_ADMIN=1` is set, and then it is Admin-only and linked nowhere in the product UI. The guard is two checks: the `/admin` page (`redirect('/settings')`) and the `(payload)` layout's server function (`notFound()`, so a POSTed server action gets 404 too). `/api` and `/mcp` are unaffected. e2e: the default server checks the redirect; `E2E_ADMIN_ENABLED=1` against a dev server started with the flag checks that an Admin reaches Payload and a non-Admin does not.

- **Who edits what** (D8, narrowed by #260): an Admin edits everything. A Bauherr edits only `budgetUnit` and the budget amount of their own Workspaces on `/settings/workspace` (model tiers, run mode, Knowledge repo, gateway key and health are Admin sections and not rendered for them; a Bauherr save leaves them untouched). Every server action in `(shell)/settings/actions.ts` re-checks the role; the UI only hides controls.
- **Writes** use the Payload local API with the current user as `user` and `overrideAccess: false` (not `fetch` to `/api`; this is the D9 implementation, not REST): same collection access, hooks and validation, no cookie/Origin round-trip. Every write also asserts that the target and the Products/Connections it references belong to the current Workspace (`lib/settings-guards.ts`). Reads in `lib/settings.ts` use `overrideAccess: true`, filtered by the current Workspace, and load `secret` and `gatewayKey` with `select: false`, so they never enter memory.
- **Validation errors**: `run()` in `lib/settings.ts` turns Payload's `ValidationError` (`errors[].path/message`, e.g. `awsRegion: required for bedrock`) into `FormState.fields`; `Field` renders the message under the input with the same `name`. Other errors show as one line next to the button; success shows "Saved". Forms submit with `startTransition` instead of a form action so a failed save keeps the typed values.
- **Workspace**: empty model tiers store the provider preset's defaults; a preset without defaults (Bedrock, Vertex, compatible endpoints) requires them. Budget amount is one input mapped to `budgetUsd30d` or `budgetTokens30d` by the unit. Spend shows when `GATEWAY_ADMIN_URL` and `GATEWAY_DATABASE_URL` are set. "Rotate key" needs a second click ("Confirm rotate"); with the gateway off it is replaced by a note.
- **API key** (`/settings/api-key`, every Bauherr, own record only): primary section **Agent keys** (`agent_keys`, `lib/api-key.ts`: `mintAgentKey` / `revokeAgentKey` / `resolveAgentKey`): "Create agent key" with a label, shown once as the `claude mcp add` line; a table with prefix, last used and "Revoke" (second click "Confirm revoke"). Agent keys cannot use gate tools ([session mode](session-mode.md#agent-identity)). Secondary section **Personal key (human)** with the warning "Never give this key to an agent; it can approve gates.": "Create/Rotate personal key" / "Revoke personal key". The personal key is the Payload API key (`enableAPIKey`, `apiKey`, encrypted at rest) is generated in `lib/api-key.ts`, shown once as the ready-made `claude mcp add` line and never logged. It is the same credential `/mcp` accepts ([session mode](session-mode.md)). `rotateApiKey(payload, user)` / `revokeApiKey` take the signed-in Bauherr and assert `user.id`; they are the one write that uses `overrideAccess: true`, because Payload's `canCreateOrUpdateAPIKey` is admin-only and this is self-service. The connect line uses `PUBLIC_URL` (fallback `http://localhost:3000`), never the Host header. "Rotate key" is the primary button; "Revoke key" is a plain button with danger text in its own section.
- **Audit** (`/settings/audit`, Admin only, others get 404): tabs Touches (factory rows, actor `factory`, show a muted Factory label) and Tool calls of the selected Workspace, newest 200, filters Ticket (`#12` or `repo#12`, repo = repository full name or Product slug; shown as `<repo>#<number>`), Run id (malformed values show a field error) and (touches only) actor (substring, `%`/`_` escaped), linking to Ticket and Run pages.
- **Workflow** (`/settings/workflow`, Admin only): "Where you are asked" is the gate ladder (Answer questions "Always on", Approve the plan, Accept on staging, Ask me before production as "On for every Product" or "Per Product"); one `Details` disclosure holds when, what you do and where, the read-only stage table of `pack/workflow.yaml` with the mode each stage resolves to in the Workspace (`modeFor` precedence), steps, and the latest `workflow_versions` row per Product; "differs from base" marks a compiled workflow that is not the base (Knowledge overlay).
- **Knowledge editor** (`/knowledge/edit?path=<repo path>`): edits one `.md` file of the Workspace's Knowledge repo. The heading is the document title and the text area is labelled "Document text". Save opens a PR `bauherr/edit-<ts>`; the `watch-knowledge-prs` job squash-merges it once its checks are green. The owner only reads "Saved. Your change goes live once its checks pass." (no PR number or link; the PR shows in the Admin Write-backs table). A stale save shows the changes from the current version to the submitted one and is not written; a PR that cannot merge is recreated once, then commented `needs-you`.
- **Factory health** (block on `/settings/workspace`, Admin only): `payload-jobs` queued / running / failed of the last 24 h (instance-wide, `payload.count` per state), age of the oldest queued job (looked up within 7 days), last poll per source (`ticket_sources.lastPolledAt`, written on every poll attempt; `lastError` shown in danger color when the last attempt failed), gateway budget as a word (OK, Near limit, Exhausted, No limit, Gateway off). Below it a "Flaky checks" table: the top 5 checks of the last 30 days that passed after a retry (`check_flakes` with outcome `flake` of the Workspace), with count, last seen and the Ticket; empty text when there are none.
- **Products**: delete is offered only when no repository, ticket source, ticket or workflow version references the Product (the reason is shown otherwise).
- **Connections**: preset fields come from `PRESETS[preset].required`; the secret is write-only (empty = unchanged). "Verify again" (every kind): an LLM provider is re-saved unchanged, which runs the `afterChange` verify; a GitHub or GitLab Connection asks the forge who the token belongs to and stores `capabilities.verifiedAt` or `lastError` (a new secret clears them).
- **Bauherren**: a new Bauherr gets a server-generated temporary password, shown once in the form result and never logged. `oidcSubject` links an existing Bauherr to SSO (`<issuer>|<user ID>`, see `docs/auth.md`); the table shows only a linked flag, the raw subject appears in the Admin edit drawer. Non-Admins see only Bauherren sharing the current Workspace, with Workspaces reduced to their own. ## Theming

`pnpm --filter server tokens` generates `(app)/tokens.css` from `docs/design/tokens.json` (also run by `predev`/`prebuild`; commit the result). Light and dark follow `prefers-color-scheme`; the avatar-menu Theme row (System / Light / Dark, menu stays open) sets `data-theme` and stores it in `localStorage` (`bauherr-theme`). Pages use Tailwind utilities and shadcn components; `app.css` keeps only the legacy rules still in use: the Requests page, the Intake chat, the Products pages with the form primitives (`SettingsForm.tsx`, `SettingsParts.tsx`) and a few shared helpers (`.muted`, `.small`, `.stack`, `.err`); it shrinks as they move.

## Add a page

Create `(app)/(shell)/<path>/page.tsx` as a server component, call `currentWorkspace()`, build from `components/` and the token variables. Add a nav entry in `components/Nav.tsx` only for daily-business pages; settings are reached via the avatar menu.

## E2E

`pnpm e2e` (Playwright, from `apps/server`) runs against `BASE_URL` (default `http://localhost:3000`) with `E2E_EMAIL` and `E2E_PASSWORD_FILE`. Needs `npx playwright install chromium` and the system libraries it lists.

## Smoke test

`pnpm --filter server seed:e2e` seeds the e2e DB (admin, Workspace, one ticket). The e2e suite expects a freshly seeded DB (re-runs leave active Runs behind). `pnpm e2e` reads `BASE_URL`, `E2E_EMAIL` and `E2E_PASSWORD_FILE`. Payload accepts the session cookie only from the `serverURL` origin (`PUBLIC_URL`); from another origin run Chromium with `--host-resolver-rules=MAP localhost <host-ip>` (or leave `PUBLIC_URL` unset on the dev server).

CI (`.github/workflows/ci.yml`) runs the suite twice, seeded via `seed:e2e`. Job `build-image` builds the production image once per run (`Dockerfile`: manifests and `pnpm install` first, so that layer is reused until a manifest or the lockfile changes; layers cached with the GitHub Actions cache via `docker/build-push-action`, `cache-from/to type=gha,mode=max`) and hands it on as the artifact `image`; jobs `e2e` (`docker compose up --no-build`) and `cli-smoke` (retags it as the version the CLI pins) load it instead of building. `production.yml` and `release.yml` still build from the tested SHA and read the same layer cache. Job `e2e` uses that image; the image refuses `BAUHERR_E2E_FAKE_FORGE`, so the fake-forge specs are skipped there. Job `e2e-fake` builds with `BAUHERR_TEST_BUILD=1` and runs `next start` (no first-hit compile; it migrates on boot, so `seed:e2e` runs after the server is up) with `BAUHERR_E2E_FAKE_FORGE=1 INTAKE_FAKE=1 BAUHERR_PACK_DIR=<abs>/apps/server/tests/fixtures/gated-pack` and Playwright with `E2E_FAKE_FORGE=1 E2E_GATED_PACK=1` (the gated pack turns the plan gate on) and runs those specs, sharded in two (`--shard=N/2`, one Postgres and server per shard; specs must not depend on each other across files). On a pull request, shard 1 then runs every spec file the PR adds or changes (`git diff --diff-filter=AMR` against the base, `apps/server/e2e/*.spec.ts`) in 3 further passes (`apps/server/scripts/e2e-burnin.sh`), each on a fresh DB (schema reset, server restart, `seed:e2e`), so a flaky new test turns the PR red; `apps/server/scripts/e2e-isolation.sh` checks that every spec file passes alone and in reverse order on a freshly seeded DB. Push-to-main CI and unchanged specs are not repeated. All jobs cache the pnpm store via `actions/setup-node` (`cache: pnpm`, keyed on `pnpm-lock.yaml`).

Local fake-forge run: on a fresh DB, `BAUHERR_TEST_BUILD=1 pnpm build`, start `BAUHERR_E2E_FAKE_FORGE=1 INTAKE_FAKE=1 BAUHERR_PACK_DIR=$PWD/tests/fixtures/gated-pack pnpm exec next start --port <port>` from `apps/server`, run `seed:e2e`, then run `npx playwright test` with `E2E_FAKE_FORGE=1 INTAKE_FAKE=1 E2E_GATED_PACK=1` (plus `BASE_URL`, `E2E_EMAIL`, `E2E_PASSWORD_FILE`). Drop `E2E_GATED_PACK` and `BAUHERR_PACK_DIR` to run against the default pack. `next dev` (migrate and seed first) works without the marker. Only the OIDC and admin-disabled specs stay skipped in both (they need dedicated servers).
