# UI

The Bauherr UI is the Next.js route group `apps/server/src/app/(app)/`, served at `/`. Payload's REST API stays at `/api`, MCP at `/mcp`; `/admin` redirects to `/settings` unless `BAUHERR_ENABLE_ADMIN=1`.

**Render rule**: a page render reads only the database. GitHub, GitLab, the gateway database and Jaeger are read by jobs and server actions that store what a page needs (`tickets.openCriticalDecisions`, `tickets.liveness`, `products.overlapSuggestions`), or by a component streamed through `<Suspense>` with a skeleton fallback and a 3 to 8 s `within()` that degrades to a plain line. `/settings/usage` renders its tables from the database; the 30-day USD spend (gateway database) and the Open traces probe stream. Known open: the Knowledge repo picker on `/settings/workspace` (`listRepos`) and the gateway spend badge still wait up to 3 s. `tests/render-no-forge.test.ts` fails when a page, layout or render loader (`lib/{overview,settings,run,requests,setup}.ts`) names a forge client outside its commented allow-list.

## Shell

`(shell)/layout.tsx` does the two counts (needs-you, own Drafts) and renders `components/AppShell.tsx`: a flex row `AppSidebar | content | dock`. Components: shadcn `ui/sidebar.tsx` (Radix; collapses to an icon rail, a Sheet below 768px; the state is the `sidebar_state` cookie, which the layout reads so the first paint is right; Ctrl/Cmd+B toggles), `AppSidebar`, `WorkspaceSwitcher`, `UserMenu`, `ShellHeader`, `Breadcrumbs`, `CommandMenu`.

- **Sidebar**: logo and Workspace (a menu with 2+ Workspaces, else the name) on top; main group Inbox (needs-you badge), Tickets, Requests (own-Drafts badge), Releases, Knowledge (only with a connected Knowledge repo), Runs (Admin); footer Settings and the user menu (email, Theme row, Release notes with the version, Sign out). Items and their matching rules live in `components/nav-items.ts`; every link carries `LinkPending`, tooltips show on the rail, `aria-current="page"` marks the section. Landmarks: `nav` "Main", `nav` "Account", `header`, `main#main` with a skip link.
- **Header**: sidebar trigger, breadcrumb, "New request" (outline button, hidden on `/requests/new`), search button (accessible name "Command palette", Ctrl/Cmd+K). Breadcrumb = section › page from the pathname (`Breadcrumbs.tsx`); a page sets its last label with `<PageTitle>{'#123'}</PageTitle>` (client component, context in `PageTitle.tsx`; used by Ticket, Run, Request and Product pages).
- **Command palette** (`CommandMenu.tsx`, shadcn `command` in a `dialog`): "Go to" (every sidebar destination and Settings page), "Tickets" (`searchTickets` in `lib/search.ts`: up to 8 Tickets of the Workspace by `#number` or title, database only, debounced 150 ms, runs only while typing) and "Actions" (New request, Toggle theme, Sign out). Focus returns to the search button on close.
- **Next-step bar** stays inside the content column (`sticky top-0` on desktop, so the sidebar never covers it; fixed to the bottom at 640px and below, where the sidebar is a Sheet above it). `main` pads for it via `--next-step-h`.
- **Dock slot**: `AppShell` takes an optional `dock` node rendered after the content column; nothing renders there yet (the AI chat panel goes there).

## Overview

Tabs **Workflow**, **Graph**, **Epics** on `/`, plus a Product filter and a "Show done" toggle (`?state=all`, Workflow only); the Product filter is hidden with one Product or fewer (`?product=<id>`). The chosen tab is stored per user in `bauherren.uiPrefs` (`{ view }`, written by the server action `setView`, which validates the view and merges into the freshly read prefs); `/` without `?view=` redirects to the saved one. Data comes from `lib/overview.ts` (`loadOverview(workspace, all)`: open tickets, plus the newest 200 closed ones when `all`; latest Run per ticket from one query; the newest 100 Runs of the Workspace; Products).

- **List**: "Needs you" first, then one section per stage (`triage, plan, build, review, release, done`); empty sections are omitted and a ticket in "Needs you" is not repeated below. Tickets without a stage label count as `triage`, closed ones as `done`.
- **Epics**: a Ticket with sub-tickets (or just split, stage `parent`) is an epic, never a Workflow row or Graph node. Every sub-ticket card carries an epic tag (short title, colour from the epic id, links to the epic). The `Epic` select (hidden without epics) narrows Board, Graph and Runs via `?epic=<id>`; `?view=epics` lists open epics in rank order with progress bar, `k/n done` and open sub-tickets per column, expandable to the sub-tickets (`Show done` adds closed epics). The epic's Ticket page shows the same progress and list instead of the stage pipeline; plan approval stays there (`lib/epics.ts`). The selected epic is remembered per user (`uiPrefs`) and restored when Board or Runs open without `?epic=`; `?epic=` (All) clears it.
- **Workflow view** (`/`, tab "Workflow", sidebar "Workflow"): the workflow of `factory.yaml` as a graph, then the Tickets as a table. The graph (`components/workflow/WorkflowGraph.tsx`, layout in `layout.ts`) is server-rendered from the node order alone and fluid: nodes sit at percentages of the width, the edge SVG stretches (`viewBox` in layout units, `preserveAspectRatio="none"`, non-scaling strokes), arrowheads and edge labels are HTML at the same coordinates, and CSS container queries on the wrapper (the chat dock changes the width, not the viewport) pick one of two layouts computed for different natural widths: from 900 px full cards, from 560 px compact cards (median and executors move into the tooltip, a checkpoint shrinks to a flag and its count with the name in the tooltip and `aria-label`, straight-edge labels drop), below 560 px a column (no measuring, no graph library; assistant-ui's `flow-graph` has label-only nodes and no edge labels or back edges): one card per stage, one pill per human checkpoint (refine, plan gate, staging gate, production; `human`-kind stages), outcome edges with their label, backward edges dashed below the row, edges that skip nodes as arcs above, `escalate`/`backlog` as dashed pills in the card. A stage card shows open Tickets (`count / limit` when the Workspace has a WIP limit: warning colour at the limit, danger over it), a four-segment bar and counts (in progress, waiting for you, waiting on CI, queued; the order and a legend carry the meaning, not the colour), "median <duration>" in stage over the last 30 days (`flow()`, `stageMedians` in `lib/workflow-view.ts`), the executors active there now (initials, live dot, tooltip with client, model and since) and a top border by state (attention beats active beats idle). A checkpoint pill counts the Tickets waiting at it (`checkpointOf`). Click or Enter on a node selects it: `?stage=<stage>` or `?stage=<stage>:<refine|gate|production>` filters the list, a second click clears it. Stage titles are shown capitalised by CSS; stored names are untouched. The list (`TicketList`, `SortableRows`) groups by stage in workflow order, one table per stage with the columns #, Ticket (title, epic tag, Hotfix marker), Product, Status, Who, In stage for (since the newest stage-change `ticket_events` row, else the Ticket's last update) and a row menu. A row's order is the owner's rank (`executionOrder`: Hotfix lane first, then rank, then number); drag, Alt+ArrowUp/Down and the menu move a Ticket within its lane via `rankTicketAction`. The pull order (`frontierOrder`) never reorders the list. Without a selected stage the done group is collapsed to a "Show N done" link (`?stage=<done>` opens it; "Show done" expands it too) and group headings stick to the top while their group is on screen. The columns Product, In stage for and Who appear with the list's own width (container queries, 800, 640 and 960 px); narrower, the Status cell carries the Who line. The Plan, Build, Review and Release headings read `count / limit` and link Admins to the WIP settings.

**Status vocabulary** (`lib/status.ts`, `ticketStatus(wf, row)`; shown identically in the list, Epics, the Graph tab, the chat and the Ticket page; "Working" is never a ticket status). First match wins:

| Label | When | Who | Detail |
|---|---|---|---|
| Done | closed, or still open in the done stage (detail "closing") | | |
| Split | the Ticket is in the container stage | | "into N sub-tickets (M done)" |
| In progress | a running Run of the Ticket's own stage | session: label or owner, client name and version, model; runner: "Bauherr runner", model | verb of the Run kind (triaging, planning, building, reviewing, deploying), since when; escalated or investigating |
| Queued | a queued Run or a Run awaiting a session | | "waiting for a session", else why (full column, overlap) or "next in line" |
| Waiting for you | `needsYou` | the notified people | the need ("Approve plan", "Answer decisions", "Accept on staging", ...; Run problems add the reason) |
| Waiting on CI / merge queue / deploy | the conditions `phaseOf` calls `ci` | "GitHub Actions" or "GitLab CI" by the Product's Connection kind | what it waits for |
| Blocked | open blockers | | "by #12, #15" |
| Failed | the Run of the stage failed or ran out of budget, nothing for the owner yet | | first line of the reason |
| Queued | otherwise | | why, or "next in line" |


- **Runs** (`/runs`, Admin): the newest 100 Workspace Runs first (Ticket, stage, status, relative time); a line says so when there are more. The `Epic` select narrows them as on the Board; the Product and Epic selects are each hidden when there is nothing to choose (one Product, no epics).
- **Graph** (`?view=graph`): columns by blocker depth. Order inside a column and in the no-dependency section is `executionOrder` (`lib/frontier.ts`): Release, Review, Build, Plan, Triage, then the rest, inside a stage the owner's rank. Only the legend is a collapsed `<details>`; the no-dependency section is always visible under "Without dependencies (N, K running)" (K shown only when > 0). The no-dependency section is a wrapping grid of small nodes grouped by stage, one heading per stage; Tickets without an execution stage (done, split) form a last group capped at the 12 newest, with an "All done Tickets" link to `/?done=1`. A Ticket whose latest Run is `running` gets `data-running` on its node and Board card: a marching dashed border (stripe on cards) and the activity word from `activity()` (`lib/format.ts`: building, reviewing, planning, deploying, triaging); `awaiting_session` is not animated. With `prefers-reduced-motion` the border is solid accent and the word stays. The Tickets page refreshes when `/api/changes` reports a change, checked every 5 s (`AutoRefresh`), so the state appears and disappears without a reload.

"Needs you" (`needsYou()` in `lib/needs-you.ts`, first match wins): `Approve plan` (stage `plan`, no `bauherr:approved:plan` label, latest Run is a succeeded plan Run), `Run needs you` (latest Run `needs_human`), `Review MR` (stage `review`), `Run failed` (an addition to D5). A plan Run that is `running`, `queued` or `awaiting_session` is "Plan in progress" and not needs-you; D5 (c): when the plan has unanswered critical decisions it reads `Answer decisions` instead of `Approve plan`. The overview makes no forge call: it reads `tickets.openCriticalDecisions`, the count of unanswered critical decisions that `submitPlan`, `postDecisions` and the minute-ly gate sweep (`syncGate`, one bounded comment read per Ticket awaiting plan approval) store through `storeOpenCritical`; a positive count turns `Approve plan` into `Answer decisions`. The Ticket page is always exact (it reads the comments live, streamed). The Tickets nav item shows the count over open tickets: one indexed `count` of `tickets.needsYou` (set, state `open`) in `(shell)/layout.tsx`, not the overview. The column is written by `syncGate` (the per-minute gate sweep visits every open Ticket) from `needsOf()` in `src/lib/needs-you.ts`, the same function `loadOverviewRows` uses for its rows, so the two cannot drift; it holds `Approve plan` where a row says `Answer decisions` (the count is the same). The human-gate actions do not write it: after approving, the badge clears with the next sweep (at most a minute). `seed:e2e` fills it itself (no sweeper in e2e). The need on a card is shown as the bar's verb (`GATES[need].verb`, e.g. `Accept on staging`, `Re-run build`); sorting and counts still use the need. A card with a notified gate carries `@login · waiting <age>` (from `tickets.gateNotified*`) in the verb's tooltip.

## Insights

`/insights` (every Bauherr; Workspace-scoped, database only). A range (`?range=7|30|90`, default 30) and the Product filter (`?product=<id>`). Data: `loadInsights` in `lib/insights.ts` over `flow()` (the Tickets whose first `ticket_events` row falls in the range) and `wipAge` (one SQL statement). Plain markup, no chart library (assistant-ui's `chart` element draws one streaming series): bars carry their value as text, every series has a label in the legend and the breakdown beside the bar, the colours are the design tokens, so dark mode and colour blindness need nothing more. No cost figures are shown.

- **Tiles**: Tickets done in the range; lead time (first event to done) median and 85th percentile; cycle time (first work to done) median; the share of the done Tickets' time spent in progress, waiting for you, waiting on CI and queued (sum of that phase over their spans, divided by the sum of all phases).
- **Where time goes**: per stage in workflow order (done and the split stage left out) a stacked bar of the median seconds per phase over the Tickets that were in that stage; the stage with the largest total is flagged "Bottleneck" and its largest phase named in words ("Tickets wait 2.1 d for a Build slot", "Tickets wait 14 h for you in Plan", "Tickets wait 10 min on CI in Review", "Build takes 3 h of work per Ticket").
- **Throughput per week**: Tickets reaching done per ISO week. **WIP age**: the ten open Tickets that have waited longest in their current stage (since the newest stage-change event, else their last update), each linking to its Ticket.

## Ticket page

`/tickets/<id>` (Workspace-scoped, 404 otherwise): decision first. In order: **ActionBar** (see below), title, Product name, the **Path** (the Workflow graph in its compact `path` variant; an epic shows its sub-ticket list instead): the stages this Ticket visited are highlighted, the current one is marked "now", the transitions it took are drawn strong and a loop such as build, review, build shows "2 rounds" (`data-testid="ticket-path"`, rounds in `path-rounds`); the **Steps** (`components/workflow/TicketSteps.tsx`, data from `lib/steps.ts` over `timeline()`): totals on top (lead time so far or final, time waiting for you, in progress, queued, waiting on CI), then newest first one entry per stage visit with its phases (label of the status vocabulary, duration, start), and per Run the executor (Session or Runner), session label, client name and version, model, provider, mode, outcome or verdict, the reason and a link to the Run (cost and tokens for Admins only); a human step says who decided what (the next event's `gate:<what>` cause and actor, else the `human_touches` row), a CI step names the provider (GitHub Actions or GitLab CI) and links the MR from the Run's `artifacts.prUrl`; the Run page lists the same metadata (kind, outcome, executor, session, client, model, provider) and links back to `/tickets/<id>#steps`; a `needs_human` Run reads "Waiting for you", never "failed"), one muted history line (`Plan approved · Accepted on staging · Approved for production`, only what is true), then the gate's decisive content and nothing else: the compact **decision card** (`DecisionCard compact`, from `tickets.decision`: recommendation, facts, links; its ask is the action bar's sentence) and the release gate (`ReleaseGate`) is the staging summary and the 60-minute notice plus the required-note "Request changes" form, which is hidden until the bar's link `#changes` targets it (`target:flex`, no JS); the other gates have no content, their sentence is the bar's. Below the gate the **owner chat** (`components/OwnerChat.tsx`, `id="answer"`, shown while a decision row exists; there is no list of decisions). Then ONE closed **Details** disclosure (`components/TicketDetails.tsx`, native `<details>`, the id `details` sits on its content so the bar's "Show details" opens it) holding: forge link, Admin-only Budget, Model tiers and merge commit, decision status, the technical idle sentence ("Nothing to do: build is running (Run #5, scheduler)", Admin-only parts for Admins), Dependencies (Blocked by / Blocks), the round-cap findings, **Plan** (shown without its `## Decisions` block), **Worklog** (markdown without its own `## Worklog` heading; answered rows are in its Decisions section; the worklog Comment is the first match, plan and decisions Comments the latest), Attachments and **Runs** (Admin: Run, Stage, Status, Duration, Evidence; others: Stage linking to the Run, Status, When, Evidence; no Mode, Cost or Run ids for non-Admins). The comment composer follows Details. Markdown is rendered by `lib/markdown.ts` (the D4 implementation: raw HTML escaped, images reduced to alt text, links only http(s)). The page renders from the database at once (title, Product, pipeline, epic sub-tickets via `loadEpic`, Details, Runs); the parts that need the forge (action bar, stage history, gate, owner chat, plan, worklog and decision status, composer) stream in behind skeletons: labels and comments are read live through the Product's ticket source with a 5 s `within()`, and if that fails the page says so.

Writes are server actions in `lib/actions.ts` over `src/lib/actions.ts` (`approvePlan`, `updateWorklog`, `requestReview`, `postDecisions`), the same functions the MCP tools `approve`, `update_worklog`, `request_review` call. `approvePlan` itself refuses while critical rows are unanswered ("Answer the critical decisions first: D2, …"), so the MCP `approve` tool does too; the UI additionally disables the button. The UI actions pass the selected Workspace id and 404 for a ticket of another Workspace. `postDecisions` runs under an in-process per-ticket mutex (double submit); multi-instance deployments need a DB lock later. Submit buttons disable while pending (`SubmitButton`).

**ActionBar** (`components/ActionBar.tsx`, copy in `lib/gates.ts`): the first element of the Ticket page in every state, `data-testid="action-bar"`. Sticky at the top on desktop, fixed to the bottom of the viewport at 640px and below. Left: one sentence for the current need; right: "Show details" (opens Details), on a release gate "Open staging" (the Product's `stagingUrl`, a text link next to Accept), at most one secondary action ("Request changes" reveals the note form on click) and exactly one primary button whose label is the verb of the step. Starts by itself."; Board cards use the same reason text. The decision box shows only while decisions are open and the plan is not approved; afterwards Details reads "Decisions: N answered". Overview cards show the same verb.

**Expedite** (`expediteAction` over `expedite` in `src/lib/actions.ts`): while a Ticket is open, not yet in `release`, not flagged, and the Workspace has the Expedite lane on, the ActionBar shows an outline "Expedite" button next to the primary action. It puts the `bauherr:expedite` label on the Ticket (and removes Triage's `bauherr:expedite-proposed`); the next poll sets `tickets.expedite`. Triage's proposal is the needs-you "Expedite?" whose primary is the same button. Settings > Board & WIP has the "Expedite lane" switch (Admin). See `docs/spec/workflow.md` "Expedite lane".

**Hotfix in the Workflow list**: a row of an open expedite Ticket carries a red `Hotfix` label (`[data-hotfix]`) and a red left edge (`data-lane="hotfix"`), and rows of the lane sort first in every stage (`frontierOrder` with `expediting`), above the owner's rank. The Product page offers "Skip staging approval for Hotfixes" (off by default; only while the workflow has the staging gate). Factory health has the row "Expedite lead time (last 5)".

**Staging gate** (backend in `src/lib/actions.ts`, UI follows): a Ticket in `release` whose `releaseState` is `on_staging` shows the staging summary Comment, and the bar links the Product's `stagingUrl` as "Open staging"; the bar's "Accept on staging" calls `acceptStaging`, "Request changes" (note required) calls `requestChanges`. Needs-you reads "Accept on staging" for that state and "Staging not confirmed" for `timed_out`. MCP: `post_staging_summary`, `accept_staging`, `request_changes`. Per-Product `stagingUrl`, deploy mode, webhook URL, required checks, gate owners (GitHub logins notified at human gates, picked from the Members with a GitHub login or added by login; empty = Admins with a GitHub login), release mode and the switch "Ask me before production" (shows the effective state: on and disabled while the workflow forces it) are edited on the Product page `/settings/products/<id>`.

**Approve production** (on by default, or per Product with "Ask me before deploying to production"): after "Accept", the Ticket page shows the bar sentence "Approve the production deploy." (needs-you "Approve production") whose button calls `approveProduction`; after a failed or timed out deploy the bar reads "Production deploy failed" with "Approve again". "Approved for production" joins the history line once the label is set. MCP: `approve_production`. Product settings: "Ask me before deploying to production", production webhook URL, production checks. ### Decision-sheet format (D6)

Rows come from the plan Comment's `## Decisions` block, one bullet each (continuation lines allowed):

`- **D<n> <title>[, critical | — critical | - critical | (critical)]**. Default: <text>. Alternative: <text>. Alternatives: <text>; <text>.`

The options are the default plus each Alternative(s) item (split at `;` and sentence ends outside parentheses and code); "critical" only counts as a suffix marker of the title (a title that merely contains the word does not block approval). Without `Default:` the default is the first sentence; a row with no alternatives is single-choice (one "Accept the default" radio). Saving posts one Comment `<!-- bauherr:decisions -->` with `D<n>: <answer>` lines (replaced on re-save) and appends `- <date> D<n> <title>: <answer>. By: <email>.` under `**Decisions**` in the worklog Comment (created from the worklog template when missing; unchanged answers are not appended again). The owner answers in one assistant-ui chat (`OwnerChat`, `startOwnerIntake` / `askOwnerIntake` in `lib/actions.ts`, intake session persona `owner`): one open row at a time, critical first; the options are chips (default first, marked recommended), a free-text answer is also accepted, recorded verbatim as one line of at most 500 characters (whitespace collapsed, so it cannot forge another `D<n>:` row) and never rewritten by the model. A fixed chip "Why does this matter?" (or a typed question) makes one cheap-tier model call (Ticket, plan and knowledge as context, no other Ticket or Workspace) that explains and records nothing and then offers a "Use my text as the answer" chip, so the model can never block an answer; without a gateway a question gets a fixed notice. A click on a listed option never calls the model. The composer takes at most 500 characters and closes after the summary. Opening the page again resumes the open session at the live head of the queue. The last answer ends with a one-line summary (`lib/owner-summary.ts`); a Triage hold is released by `postDecisions` as before. The sheet format and Comment markers are unchanged; `postDecisions` also serves the MCP tools. Only rows of the live plan are accepted.

### Decision card

One structure for every human checkpoint, stored on the Ticket as `tickets.decision` when the checkpoint opens (the gate sweep writes it with `needsYou`, only when the content changed; `buildDecision` in `src/lib/decision.ts` is the one pure builder, one entry per need) so the Inbox and the Ticket page read it from the database and say the same thing. Fields: `need`, `checkpoint`, `title`, `ask`, `recommendation`, `why` (at most 3), `options` ({label, action, primary, destructive, note, effect}), `next`, `evidence` (links), `details` (markdown, collapsed), `preparedBy` (`agent` when the plan's or staging summary's own TL;DR is the source, else `factory`), `preparedAt`, `openSince`.

Copy rules: `ask` is one sentence that starts with a verb, at most 120 characters ("Approve the plan for "Login redirect""); `recommendation` is what the factory would do and one reason, or null when it has no basis; `why` is at most three short facts (what changed, what was checked, what is at risk); every option maps to an existing server action (no new decision powers) and says what it does; plain words, no factory jargon (no Run, MR, WIP, sha). The plan card comes from the plan's leading `## TL;DR` (`tickets.planTldr`, stored when the plan is posted), the staging card from the first two sections of the staging summary (`tickets.stagingTldr`); a plan without TL;DR says "The plan has no summary; open it to read it."

An in-place decision clears `needsYou` and `decision` with a conditional UPDATE (`settleDecision`, `cas()`) and stores `decidedAt`/`decidedNeed`; the sweep does not reopen that need for 2 minutes (`justDecided`), so a decided card never comes back while the forge catches up. `decideAction` refuses a card whose need the Ticket no longer has.

## Loading states and live refresh

- **No route-level `loading.tsx`.** React holds a revealed Suspense boundary back for ~300 ms after its fallback committed, so a route skeleton made pages that render in 15-45 ms take ~320 ms instead of ~25 ms (measured). A `loading.tsx` is justified only where the seeded page's server render exceeds ~200 ms (none today).
- Click feedback comes from the link: `components/LinkPending.tsx` (child of a `<Link>`, `useLinkStatus`; in `ui/tabs.tsx`, the sidebar items, the settings nav, Board/Runs ticket links) sets `data-pending`/`aria-busy` and `app.css` pulses the link; `components/NavProgress.tsx` (top of the shell) shows the `#nav-progress` bar from a click on an internal link until the URL changed (also when the clicked link unmounts), CSS only, 10 s give-up. The Product/Epic selects navigate in `useTransition` with `aria-busy` and `ui/loading-state.tsx` (assistant-ui `GenerationLoader`, added by hand: the registry item needs `tw-shimmer`).
- Skeletons (`components/ui/skeleton.tsx`, `components/PageLoading.tsx`: `aria-busy`, `data-testid="page-loading"`, static CSS) are for Suspense around genuinely slow sections inside a page. Knowledge streams its forge-backed Write-backs and Skill proposals that way (they cost ~200 ms per view); the first view of a Workspace also builds its Knowledge index (about a second, once, `indexedOnce` in `src/lib/knowledge.ts`).
- `AutoRefresh` (Tickets page) polls `GET /api/changes` every 5 s and calls `router.refresh()` only when `v` changed; it pauses while the tab is hidden or a refresh is pending. `/api/changes` (`src/app/api/changes/route.ts`, session required, 401 otherwise) answers `{ v }`: the newest `updated_at` of the selected Workspace's Tickets and Runs as epoch ms, from one SQL query.
- Fonts are vendored (`(app)/fonts/`: Archivo variable and IBM Plex Mono 400, Latin subset, SIL OFL, licences next to them) and loaded with `next/font/local` (`display: swap`); the build needs no network. `app.css` puts the loaded families first in `--font-sans`/`--font-mono`.
- Budget, `e2e/perf.spec.ts` (plain `e2e` job, production server): timestamps come from a MutationObserver in the page, not Playwright polling. After a click on each main nav target, settings page, a Ticket and a Run, something pending (link pending state or progress bar) or the content is visible within 100 ms and the content within 400 ms; one `PERF <route> pending=<ms> content=<ms>` line per route.

Open state is `html[data-chat=open]` and width `--chat-w`; both are set before first paint by a small inline script (restored only at desktop width) and the markup is always rendered and shown by CSS, so there is no layout shift. State is also saved in `localStorage` (`bauherr-chat:<user id>`).
- **Lazy**: the heavy part (`ChatPanel.tsx`: assistant-ui, markdown) is a `next/dynamic` import (`ssr: false`) mounted on first open and kept mounted afterwards, so a running answer survives closing and client-side navigation. A page that never opens the chat downloads only the button.
- **Runtime** (`runtime.ts`, `adapter.ts`, `api.ts`): thread list over `/api/chat/threads` (the server names a thread from the first user text; `generateTitle` refreshes the item after the first run), per thread a local runtime whose `ChatModelAdapter` POSTs `/run` (or `/confirm` when a card was just decided) and builds parts from the NDJSON lines. History is `GET`/`PUT .../messages`, the `answerId` of `done` rides in the message metadata and is sent with the PUT. The last open thread is remembered per person and reopened if it still exists. A pending card is put back from `pending` when the stored message lacks it.
- **Context**: `context: {path}` is read from `location` at send time. The chip above the composer (`GET /api/chat/context?path=`, refetched on navigation) opens a popover with the context markdown; a reopened thread whose stored path differs from the current page says "This chat was about <label>" with a link.
- **Widgets by kind** (`tools.tsx`): `read` is a one-line receipt (summary, ok/failed, expandable result); `confirm` is an approval card with the `details` rows, Approve / Decline (Decline asks for an optional reason), a destructive style when flagged, and no buttons after a decision. After an approved write `router.refresh()` updates the page behind the dock. `#123` in answers links to `/tickets/n/123`: straight to the Ticket when the number is unique in the Workspace, else a small chooser with the Products.
- **Images**: paste, drop anywhere on the composer, or the attach button; each image uploads to `/api/chat/media` (errors inline, at most 6 per message), is sent as `{type: 'image', mediaId}` and shows as a thumbnail that opens in a dialog.
- **Feedback**: thumbs up sends at once; thumbs down opens reason chips and a note, both through the runtime's `FeedbackAdapter`. Admins read them at `/settings/chat-feedback` (table from `chatFeedback()`, filter by rating).
- **Local slash commands** (never sent): `/context`, `/new`, `/help`.
- Elements: composed from `@assistant-ui/react` primitives (Thread, Composer, Message, ActionBar, ThreadList, Attachment) styled with the shadcn tokens, with `@assistant-ui/react-markdown` for markdown and `shiki` for highlighting (`highlight.tsx`: loaded only when a message has a fenced code block, one light and one dark theme, grammars fetched per language from ts, tsx, js, json, bash, yaml, sql, diff, md, python, php); the registry elements import `lucide-react`, which the repo does not have.

## Theming

`pnpm --filter server tokens` generates `(app)/tokens.css` from `docs/design/tokens.json` (also run by `predev`/`prebuild`; commit the result). Light and dark follow `prefers-color-scheme`; the user menu's Theme row (System / Light / Dark, menu stays open) or the palette's "Toggle theme" sets `data-theme` and stores it in `localStorage` (`bauherr-theme`). Pages use Tailwind utilities and shadcn components; `app.css` holds no component classes any more (`.btn`, `.chip`, `.table`, `.field`, `.sform`, `.toggle`, `.rcard`, `.muted`, `.stack`, `.err` … are gone): only the font variables, the base `body`/focus rules and the `#nav-progress` and link-pending styles. Forms use `ui/label.tsx`, `ui/input.tsx`, `ui/textarea.tsx`, `ui/native-select.tsx`, `ui/checkbox.tsx`, `ui/switch.tsx` (native inputs, so forms post as before), `ui/alert.tsx`, `ui/card.tsx` and `ui/table.tsx`; `.small` is the token type style from `tokens.css`.

## Add a page

Create `(app)/(shell)/<path>/page.tsx` as a server component, call `currentWorkspace()`, build from `components/` and the token variables. Add a sidebar entry in `components/nav-items.ts` (`mainItems`) only for daily-business pages; settings are reached via the sidebar's Settings item menu.

## E2E

`pnpm e2e` (Playwright, from `apps/server`) runs against `BASE_URL` (default `http://localhost:3000`) with `E2E_EMAIL` and `E2E_PASSWORD_FILE`. Needs `npx playwright install chromium` and the system libraries it lists.

## Smoke test

`pnpm --filter server seed:e2e` seeds the e2e DB (admin, Workspace, one ticket). The e2e suite expects a freshly seeded DB (re-runs leave active Runs behind). `pnpm e2e` reads `BASE_URL`, `E2E_EMAIL` and `E2E_PASSWORD_FILE`. Payload accepts the session cookie only from the `serverURL` origin (`PUBLIC_URL`); from another origin run Chromium with `--host-resolver-rules=MAP localhost <host-ip>` (or leave `PUBLIC_URL` unset on the dev server).

`e2e/chat-dock.spec.ts` needs the server started with `CHAT_FAKE=1` (scripted model, set it in the CI job and pass `-e CHAT_FAKE` to the Playwright container); its approval cases use seeded Tickets #28 and #29 and the second member `chat-other@example.com`.

CI (`.github/workflows/ci.yml`) runs the suite twice, seeded via `seed:e2e`. Job `build-image` builds the production image once per run (`Dockerfile`: manifests and `pnpm install` first, so that layer is reused until a manifest or the lockfile changes; layers cached with the GitHub Actions cache via `docker/build-push-action`, `cache-from/to type=gha,mode=max`) and hands it on as the artifact `image`; jobs `e2e` (`docker compose up --no-build`) and `cli-smoke` (retags it as the version the CLI pins) load it instead of building. `production.yml` and `release.yml` still build from the tested SHA and read the same layer cache. Job `e2e` uses that image; the image refuses `BAUHERR_E2E_FAKE_FORGE`, so the fake-forge specs are skipped there. Job `e2e-fake` builds with `BAUHERR_TEST_BUILD=1` and runs `next start` (no first-hit compile; it migrates on boot, so `seed:e2e` runs after the server is up) with `BAUHERR_E2E_FAKE_FORGE=1 INTAKE_FAKE=1 BAUHERR_PACK_DIR=<abs>/apps/server/tests/fixtures/gated-pack` and Playwright with `E2E_FAKE_FORGE=1 E2E_GATED_PACK=1` (the gated pack turns the plan gate on) and runs those specs, sharded in two (`--shard=N/2`, one Postgres and server per shard; specs must not depend on each other across files), with `E2E_WORKERS=3 E2E_RETRIES=1` (a test that passes on retry shows as flaky in the report; the burn-in runs 3 workers, no retries). On a pull request, shard 1 then runs every spec file the PR adds or changes (`git diff --diff-filter=AMR` against the base, `apps/server/e2e/*.spec.ts`) in 3 further passes (`apps/server/scripts/e2e-burnin.sh`), each on a fresh DB (schema reset, server restart, `seed:e2e`), so a flaky new test turns the PR red; `apps/server/scripts/e2e-isolation.sh` checks that every spec file passes alone and in reverse order on a freshly seeded DB. Push-to-main CI and unchanged specs are not repeated. All jobs cache the pnpm store via `actions/setup-node` (`cache: pnpm`, keyed on `pnpm-lock.yaml`).

Local fake-forge run: on a fresh DB, `BAUHERR_TEST_BUILD=1 pnpm build`, start `BAUHERR_E2E_FAKE_FORGE=1 INTAKE_FAKE=1 BAUHERR_PACK_DIR=$PWD/tests/fixtures/gated-pack pnpm exec next start --port <port>` from `apps/server`, run `seed:e2e`, then run `npx playwright test` with `E2E_FAKE_FORGE=1 INTAKE_FAKE=1 E2E_GATED_PACK=1` (plus `BASE_URL`, `E2E_EMAIL`, `E2E_PASSWORD_FILE`). Drop `E2E_GATED_PACK` and `BAUHERR_PACK_DIR` to run against the default pack. `next dev` (migrate and seed first) works without the marker. Only the OIDC and admin-disabled specs stay skipped in both (they need dedicated servers).

Page speed (on demand, not in CI): with the fake-forge server above running on a production build, `apps/server/scripts/measure-pages.ts` (needs `BASE_URL`, `E2E_EMAIL`, `E2E_PASSWORD_FILE`; run it in the Playwright image like the specs) prints the median TTFB and load of `/`, a Ticket page and `/settings/workspace`, 5 cold (fresh browser context) and 5 warm (repeat loads) each. `loadOverview` and `loadOverviewRows` are the same database-only loader (the newest Run per Ticket is one `DISTINCT ON` query); the Ticket page reads its epic with `loadEpic`. Forge reads that remain on a page are streamed and carry a timeout (`within`).
