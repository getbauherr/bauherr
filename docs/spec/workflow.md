# Workflow spec (v0.1)

The single human-readable spec of the Bauherr workflow. Rules live in the core pack; this page links to them and does not repeat them. Decisions: #10 (workflow), #37 (Run contract), #36/#39 (team patterns).

## 1. Stages and labels
Triage → Plan → Build → Review → Release → Done, declared in `pack/factory.yaml` (see the end of §14).

`runs.stage` and `tickets.waiting_for` are plain text validated against the workflow (`lib/stage-text.ts`), not Postgres enums; `runs.kind` records the stage kind a Run ran for (`scan` and `distill` for the system Runs), filled on create. The WIP advisory lock is keyed by `hashtext('wip:<stage>')`.

- The Stage is a Label in the Ticket source: `bauherr:stage:<name>` (the same on GitLab: scoped `stage::` labels are Premium+). Bauherr derives it and never stores it as truth. Moving a stage adds the new label before it removes the old one (with two labels the later stage wins); when the forge lost the label, the stored stage wins and `poll-tickets` restores the label.
- Other labels: `bauherr:go` (start), `bauherr:approved:plan` (plan gate; set only while the plan gate is on, which is the default), `bauherr:approved:staging` (staging gate; with the release gate off the factory sets it itself when staging is confirmed), `bauherr:blocked` (needs a person).

| Stage | Agent work | Ends with |
|---|---|---|
| Triage | cheap triage Run per open, unassigned Ticket without a stage label ([triage](../../pack/skills/triage/SKILL.md)); a Ticket carrying one of the stage's `exclude_labels` in `pack/factory.yaml` (`wayfinder:map\|grilling\|research`) is not triaged; no gate, but a `refine` hold shows the owner an "Answer questions" Gate (assignee + mention, #77) | `plan`: stage label plan; `refine`: label `bauherr:needs-refinement` + a decision-sheet Comment for the owner, the stage label plan once every critical question is answered; `skip`: reason Comment, no stage. Re-triaged only when the Ticket changes; at most 5 new Triage Runs per Workspace per poll, and after 3 failed, invalid or expired attempts one Comment stops it until the Ticket changes. Session Runs end with `submit_triage`; autonomous Runs write `.bauherr/triage.json` (no shell, writes only under `.bauherr/`) and the server applies it through the same validation |
| Plan | plan Run | plan Comment (Goal, Steps, Files) + Goal in the worklog (+ Sub-tickets if large) |
| Build | build Run | MR Linked on the Ticket |
| Review | review Run: reviewer without memory of the change ([review](../../pack/skills/review/SKILL.md)) | review Comment on the MR; merge or back to Build |
| Release (shown as Staging) | none; Bauherr observes the Product's CI (or a deploy webhook) after the MR merged | staging summary Comment + staging acceptance |
| Done | none | Ticket closed `completed` on staging acceptance (never on merge) |

Pre-review (Build): a Build whose MR-only diff has 30 or more changed lines ends with a self-review on the Workspace `cheap` tier (review rubric, at most 20% of the Run budget, no separate Run) and one fix pass for its high and medium findings; low findings and the line `Self-review: <n> findings, <m> fixed` go into the Evidence. The autonomous Runner does this before it pushes; a session Run does it as a skill duty ([run-contract](../../pack/skills/run-contract/SKILL.md)), shown in its Evidence. Then the Product's `reviewChecks` (Settings > Products, one rule per line; empty = off) run on the changed file paths only, never on a language: `src/** => tests/**` (changed source needs a changed test file, and test files named in the Evidence must exist), `schema: <globs> => <globs>` (a changed schema file needs a changed migration file) `ran: <command>` (the Evidence shows each such command with exit code 0 and names the pushed head SHA; it checks the record, CI stays the source of truth) and `evidence` (the `## Evidence` plan-step table has a `done` or `deferred` row per plan step). A failing check blocks `request_review` (and `finish_run` with an MR) with the failing lines and the Ticket stays in Build; `run_checks` returns the same list. The Runner gets one fix pass, then the Run ends `failed` without pushing.

Config per stage: label, gate (`human` or absent; see §2), max runs, and the stage's **steps** (§15). The workflow is config in Git, compiled into a versioned Postgres row on change (§15).

## 2. Gates and approvals
Human gates are workflow config in the Workspace's factory file (`pack/factory.yaml` by default). Default: three human touch points, **refine** (Triage's questions, always on), **plan** (`gate: human` on `plan`, on by default: every plan waits for the owner) and **production** (`production_gate: human` on `release`, on by default; a Product without `productionChecks` shows the visible gate "Configure production checks" (Ticket page, links to `/settings/products/<id>#production`, listed in needs-you) until checks exist, then the normal "Approve production" gate; if `production_gate` is removed from the workflow, a staging-confirmed Ticket goes to `done`). **Staging** (`gate: human` on `release`) is optional and off by default. A factory file without `gate: human` on `plan` (e.g. `tests/fixtures/bare-pack`) lets a Ticket triaged `plan` reach a merged MR and the production gate without an owner touch. `humanGates()` in `apps/server/src/lib/mode.ts` lists the enabled gates (also for the label-actor guard, #174). Per-Product overlays are §15.

| Gate | Before | Approval lives in |
|---|---|---|
| Plan approval (human, on by default: `plan` `gate: human`) | Build | label `bauherr:approved:plan`, set in the Bauherr UI or in the forge |
| MR gate (factory) | merge | clean review + green checks + `## Evidence` + Product `autoMerge` (below); merges directly, or enqueues in the forge's merge queue (Product `mergeMode`, below); no human |
| Staging acceptance (human, optional: `release` `gate: human`) | Done, or Production approval with a production gate | label `bauherr:approved:staging`, set in the UI |
| Production approval (human, default on via `production_gate: human` on `release` (a Product can also turn it on with `productionGate`); without `productionChecks` the Ticket shows "Configure production checks" first; with the workflow gate off the Ticket goes to done) | deploy | UI Gate or MCP `approve_production` (records the human touch); the label `bauherr:approved:production` is an output signal only, set by the factory after such an approval, never an approval itself |

Gate off: with the plan gate off, `poll-tickets` (`advancePlan`) moves a Ticket in `plan` whose latest Run is a succeeded plan Run to `build` (or `parent`) once a plan Comment exists and no critical decision is open; it adds no `bauherr:approved:plan` label, records no human touch and posts one audit Comment; Sub-tickets are created labelled `bauherr:stage:build` only. With the release gate off, `watch-release` runs the acceptance step itself once staging is confirmed (label `bauherr:approved:staging`, then the production gate (on by default, else `done` and closed)), without a touch; `timed_out` stays a blocker. The needs-you values Approve plan, Answer decisions and Accept on staging appear only while their gate is on; the Board's "needs you" is then refine questions, the production gate and declared blockers (Run needs you, Staging not confirmed, Round cap reached, Run failed).

Plan summary: a plan starts with a required `## TL;DR` section of labelled lines `Decision:`, `Recommendation:`, `Why:` (1 to 3 bullets), `Risk:` and optionally `Options:` (`src/lib/tldr.ts`). `submit_plan` refuses a plan without them and lists the missing lines (a hotfix plan is exempt; plans already posted are never re-checked); the parsed block is stored as `tickets.planTldr`. An autonomous plan without TL;DR is posted anyway and its card says to read the plan. Every checkpoint is shown as a prepared Decision (Inbox, Ticket page): see [ui](../ui.md#decision-card).

Gate labels (`bauherr:approved:plan`, `bauherr:approved:staging`; list in `apps/server/src/lib/gate-labels.ts`): `poll-tickets` accepts one only if the actor of its latest forge `labeled` event is a gate owner or Admin login (Product `gateOwners`, plus every Admin `githubLogin`), or is the factory's own credential and the factory recorded the approval itself (human touch `approve:plan`, `approve:inherited` or `accept:staging`, written before the label). Any other actor: the label is removed and one Comment (`<!-- bauherr:label-rejected:<label>:<time> -->`) points at the Approve button; the Ticket does not advance. A manually set label from an accepted owner records a human touch with that login. If the actor cannot be read (events call fails, no event), the label counts as not approved, is not removed, and is checked again on a later poll. Agent sessions that run with the owner's own token are therefore rejected like strangers; a separate forge identity for agents (#26) is the later alternative. A solo owner whose login equals the factory credential approves through the UI or MCP, not by hand-labelling. The plan label of a gate that is off is stripped the same way (the factory writes it only while the gate is on; gate-off Tickets advance without it).

Stage labels are trusted for backward moves only: `poll-tickets` accepts a forward move (triage < plan < build < review < release < done) only when the factory recorded it (`tickets.factoryStage`, written by `moveStage` before the label, cleared on the next poll that sees the label equal it or change). An unrecorded forward move, also one set by hand by the owner, is reverted to the DB stage with one Comment (`<!-- bauherr:stage-rejected:<stage>:<time> -->`) and starts no Run; the first sight of a Ticket is accepted. A Ticket with an open critical decision is held at the approved-plan event (the plan-to-build move); other forward moves are not blocked by it. Owners move forward through the UI, not by hand-labelling; a separate agent identity (#26) is the later alternative.

Gate tools over MCP (`approve`, `accept_staging`, `grant_review_round`, `stop_review`, `request_changes`) are human-only: `/mcp` refuses them for an agent key, see [session mode](../session-mode.md#agent-identity).

Sub-tickets: a plan may end with a `## Sub-tickets` section, one list item per child: `- **Title** — one-line body` (body may continue on indented lines, e.g. acceptance criteria; an indented `after: <sibling title>` line, exact title of another item in the section, makes the child blocked by that sibling: forge `addBlockedBy` plus local `tickets.blockedBy`, so claim_next and the frontier skip it until the sibling is closed; an unknown title is ignored with a logged warning; no implicit chain). On plan approval (UI, MCP `approve`, or the `bauherr:approved:plan` label seen by `poll-tickets`) the factory creates each listed item as a forge sub-issue (`addSubTicket`; GitLab Free, which has none, uses a `Parent: #n` body line) labelled `bauherr:stage:plan` and `bauherr:approved:plan`, so Build starts without a second approval, and records `tickets.inheritedApprovalFrom`. Inheritance rule: only items listed at approval time inherit; the factory never adds `approved:plan` to a child created later, and an approval label a human sets on a child is an ordinary manual approval. Creation is idempotent (children matched by title, also against local child rows whose forge link failed, which are only linked, never created again; the parent leaves stage `plan` only after all exist). The parent moves to stage `parent` (shown as "Split" on the Board, n/m done, no Runs) and closes with a Comment listing the children once all are closed (`poll-tickets`). Nested children and moving children between parents are out of scope.

Files: a plan lists the paths it will change in a `## Files` section, one path glob per line (bullets and backticks are stripped; parsed by `planFiles` in `app/(app)/lib/plan.ts` next to `subTickets`). The run contract tells the Plan Run to write it. Only paths and globs count, so the rule is language-agnostic.

**Progress comment.** A person who files an issue (or a request through the Requests page or the widget) may never open the factory, so the factory says in plain words where the issue is. `lib/progress.ts` `progressOf(wf, ticket, facts, template)` derives one of 15 keys (received, question, planning, approval, building, reviewing, agent, human, staging, waiting, released, stuck, closed, split, blocked) from `ticketStatus()` (the one status every page shows) plus the stored `needsYou`, `liveness` and release fields, by stage KIND; a custom `agent` or `human` stage uses its `title`, stage names never appear. The text is the Workspace's `progress` template (one section per key: first line headline, `Next:` line, other lines detail, `{{placeholder}}` lines drop out when empty). `syncProgress` keeps ONE Comment on the issue, marked `<!-- bauherr:progress -->`: headline, detail, next step and the six-step path (Received, Planned, Built, Reviewed, On staging, Released, current marked), edited in place. The body hash is claimed on `tickets.progressHash` (cas) before the write and released when it fails, so an unchanged state makes no forge call, an update is one call (`tickets.progressCommentId`; the first post lists once to adopt an existing marked Comment), and a forge failure is logged and retried by the next sweep. The first Comment is written only by the `sync-progress` job that `record()` queues for every non-sweep transition (3 retries; it throws when the forge refuses), so an existing Ticket gets its Comment at its next transition and a new one at its first, and an upgrade posts nothing on untouched issues. The `notify-gates` sweep after the gates only HEALS Tickets that already have a progress Comment (`progressHash` or `progressCommentId` set; open ones, and closed ones for 2 days after their last write) and never creates one. No request path calls the forge. Editing a Comment mails nobody, so on arrival at `question`, `staging`, `released` or `stuck` one NEW Comment `<!-- bauherr:progress-notice:<key> -->` mentions the issue's author (`Ticket.author`; only them), once per arrival (`tickets.progressNotified`, claimed before the post, cleared when the Ticket leaves the key; a second `stuck` episode posts again). Nobody is mentioned when the author is the factory's own account or a bot (Intake issues are filed by the factory credential) or is a gate owner that `syncGate` already mentioned for the current gate, so the two never double-post. Switch: `workspaces.progressComments` (Settings > General, default on; off = no Comment and no notice); there is no per-Product override.

**Notifying the gate's person.** Every needs-you value (Approve plan, Answer decisions, Accept on staging, Staging not confirmed, Configure production checks, Approve production, Production deploy failed, Release failed, Run needs you, Run failed) is a human gate. The scheduled task `notify-gates` (every minute) assigns the gate's people on the forge issue (`products.gateOwners`, else the Admin Bauherren with a `githubLogin`) and posts one `<!-- bauherr:gate:<value>:<sha1 of value+run id> -->` Comment that @mentions them and links the Ticket page (`PUBLIC_URL`), so GitHub notifies them. Once per gate value (`tickets.gateNotified`, `gateNotifiedAt`; Approve plan and Answer decisions count as one gate); no reminders. When the gate passes or changes, the factory unassigns exactly the logins it added (`tickets.gateAssignees`) that do not own the next gate; other assignees stay. Failed claims are retried each minute and a gate counts as notified only once every owner is assigned. Without owners nothing is notified; when every owner is rejected for good (unknown or unassignable login) the gate is not marked notified, `tickets.gateUnreachable` shows "no reachable owner" in the overview, and it is retried each minute. A login with a running session Run stays assigned when the gate passes. A session Run's release unassigns only its own login.

Review: a Ticket entering `review` with a factory MR gets a Review Run (mode follows the Workspace; session Runs end with `submit_review`, autonomous Runs write `.bauherr/review.json`). It posts one `<!-- bauherr:review -->` Comment on the MR: verdict, findings (severity, file:line, defect, scenario), Open. The verdict is `changes` iff a high or medium finding exists.
- `changes`: blocking findings are appended to the worklog's Unfinished work and low findings to Open (each once; Current instructions only points to them), the stage goes to `build` and a Build Run starts on the **same MR branch** (no second MR).
- Merge mode (Product `mergeMode`: `direct`, `queue`, `train`; existing Products stay `direct`). In `queue` the merge gate enqueues the reviewed head SHA in the forge's native merge queue (GitHub `merge-async` with `merge_action: merge_queue`, GitLab merge train) instead of merging, and the Ticket's `reviewState` is `queued` (shown as "In the merge queue", `queuedAt` set) until the PR is merged; `watch-reviews` then sets `merged` and `watch-release` moves the Ticket to `release` with the PR's merge SHA, as for a direct merge. A PR behind its base is not merged with the base by the Runner in `queue` (the queue tests against current main); a conflict still is. An open PR the forge no longer reports as queued after 2 minutes was dropped by the queue: back to Build (no round) with the link to the queue run, `trainFailures` + 1, the 3rd needs a human; a head that moved while queued is dequeued and reviewed again; queued for over 2 hours needs a human. A queued PR is never pushed to: `dequeueBeforeChange` takes it out of the queue before a return to Build and before a Build Run starts on it. The forge refusing the enqueue counts as a failed merge. Onboarding and "Re-detect" (Settings > Product > Merging) choose `queue` when the forge has a native queue and the repo preflight passes (GitHub: every workflow that produces a required check has a `merge_group` trigger and no deploy or publish job runs on `merge_group`; GitLab: `merge_request_event` rules in `.gitlab-ci.yml`, merged-results pipelines and trains on), else `train`; the problems are stored in `mergePreflight` and shown on Settings. Saving `queue` or `train` by hand re-runs the preflight and is refused while it has problems.
- Train (`mergeMode` `train`, forges without a merge queue; `runTrains` in `lib/train.ts`, run by `watch-reviews` right after `watchQueued`). The merge gate only marks the reviewed head `queued`. Per Product one train runs at a time: the `queued` Tickets in `executionOrder` (Board rank, then number), at most the Workspace's Review WIP limit (3 by default), are merged one by one into the branch `bauherr/train` (reset to the default branch first, force-set only that branch); a PR that conflicts goes back to Build (a conflict return, as in the Runner main-merge). CI runs on the tip (`push` to `bauherr/train`; preflight requires the trigger, GitLab: a pipeline on the branch), judged by the Product's `deployChecks`. Green: the PRs are squash-merged onto main in train order, each pinned to its tested head (`expectSha`); a moved head, a Ticket that left `queued` or a moved main rebuilds the train instead. Red: bisect: the branch is reset to prefix lengths (binary search, at most log2 k extra runs, state in `trainState`: `probe`, `results`, `tip`) until the first failing PR is known; the PRs before it were tested green and merge, it goes back to Build with the failing check's link (no round, `trainFailures` + 1, the 3rd needs a human) and the rest re-train on the new main. No force fast-forward: main is never rewritten, each PR is squash-merged onto a main that did not move since the train was built, so the tested tree and main's tree are the same. Checks still pending after 2 hours release the train and every member needs a human. `trainState` writes are compare-and-set.
- `clean`: the merge gate squash-merges (pinned to the reviewed head SHA) and deletes a same-repo branch when all of this holds. The MR is an open, non-draft factory MR (same repo, head branch `bauherr/<ticket>-...`) whose head is still the SHA the review covered; if the head moved, a new Review Run starts (no round). Every check run and commit status on the head passed; no checks counts as green only once the head commit is 10 minutes old. The MR body has a non-empty `## Evidence` section. Product `autoMerge` is on (default). Checks pending or draft: `reviewState` `waiting_checks`, re-checked each minute by `watch-release`; waiting more than 2 hours, or 3 consecutive failed merges, is `needs_human`. Checks red: the failed checks are first re-run once (below); a check that fails again goes back to Build with the check names. An MR the forge reports as conflicting, or as behind its base while auto-merge is on, is merged with the base by the factory server itself, in every Run mode (session and autonomous): no Build Run, no new Review Run, no human. The server queues the `merge-main` job (one pending per Ticket), which decides with git: it fetches the base, runs `git merge --no-edit origin/<base>` and pushes when the merge is clean. The merge commit is authored and committed by the factory bot (`Bauherr`), never by a session, so any session can do a delta review. At review time the Runner stores `reviewedPatchId` (`git patch-id --stable` of the MR-only diff, `git diff $(git merge-base origin/<base> HEAD)..HEAD`) on the Review Run; a session review has none, so the job takes the patch-id of the MR head before its merge; after the merge it computes it again, and when it is unchanged and the MR head is the SHA it pushed the verdict is re-bound to that head (the merge gate and checks decide). A different patch-id (or a push by anyone else) starts a new Review Run. A merge that finds nothing to merge on a head the forge still reports as conflicting or behind is counted per head (`mainMergeSha`, `mainMergeNoops`); the 3rd, or a git failure, is `needs_human`, and a merge that pushes resets the count. A newer pending `merge-main` job supersedes an older one per Ticket. Only a real conflict creates a Build Run (session or autonomous) and counts in `conflictReturns`; it is neither a round nor a failed merge, the server stores the reviewed SHA (`conflictReturnBase`), and the 4th conflict return needs a human. The agent or session resolves only the conflict markers, commits, and the delta Review Run gets the interdiff (MR-only diff at `conflictReturnBase` against the MR-only diff at HEAD) as `.bauherr/diff.patch`. Everything works on git objects only, so it is language-agnostic. `autoMerge` off, or no Evidence: a "ready to merge" Comment and `reviewState` `ready_for_human`; the merge stays with a human.
- The review output must include `checked` (correctness, over-engineering, spec-vs-plan, evidence, each with a one-line justification) and a verdict that matches its findings; otherwise the Ticket goes to `ready_for_human` and is never merged. A failure while concluding sets `needs_human` with a Ticket Comment. A review Run that holds its verdict while the Ticket is still in `review` with no `reviewState` (the app stopped before applying it) is concluded again by `watch-release` after 2 minutes, without a second MR comment. Reviewer prompts exclude the MR title and body; Ticket, plan, worklog and diff text are fenced as untrusted data.
- Round cap: each return to Build (changes verdict or red checks) is a round; after 2 rounds the first cap hit is granted by the factory itself (touch `review-cap:auto-grant`, actor `factory`, one Ticket Comment; `reviewRounds` lowered by 1, back to Build on the same MR); a later cap hit (or any after an owner grant) goes to `needs_human` (Ticket Comment). `tickets.reviewRounds` counts them and is only lowered by that factory grant or an owner grant. At the cap the Ticket page shows the Gate "Round cap reached" (needs-you) with the findings: "Grant one more round" lowers `reviewRounds` by 1, resets `reviewState` and returns to Build on the same MR (a second cap hit shows the gate again; a clean review then merges as usual); "Stop" leaves the MR open and moves the Ticket to `triage` with a Comment, `reviewRounds` kept. Both record a human touch (`review-cap:grant`, `review-cap:stop`), are owner-only (Admin or Workspace Bauherr) and refuse a Ticket not at the cap.
- A merge by the factory is no human touch; the next `watch-release` pass moves the Ticket to `release`.

Release: the scheduled task `watch-release` (every minute) moves a `review` Ticket whose MR merged to `release` and stores the merge commit. `observe-ci` Products: the commit's check runs (all, or `deployChecks`) are green; `webhook` Products: the webhook is POSTed once and `stagingUrl` answers 200. Then the factory posts one `<!-- bauherr:staging-summary -->` Comment (templated, no model: What you get, Found on the way, Decisions taken, Open, Accept). Not confirmed after 60 minutes: `releaseState` `timed_out` and the Comment "staging not confirmed". Only acceptance closes a Ticket: MRs reference it with `Refs <url>` and never `Closes/Fixes/Resolves`. If a merge closed it anyway (body keyword, commit message, manual close) and no acceptance label exists, `watch-release` reopens the Ticket once the factory MR is merged and the forge close reason is `completed`, posts one `<!-- bauherr:reopened -->` Comment and continues. A `not_planned`/`duplicate` close, or a close before any factory MR merged, is respected: the Ticket is set to `done` with one `<!-- bauherr:dropped -->` note; accepted Tickets are settled to `done` the same way. Every closed review/release Ticket is decided in its first pass and no longer matches the query. A Workspace Bauherr accepts (stage `done`, or held in `release` as `productionState` `awaiting_approval` while the production gate is on) or requests changes with a note (worklog Current instructions, stage `build`, new Build Run).

Poller: every forge call aborts after 30 s (gateway admin 10 s) and fails the job so the next tick runs; `expire-sessions` and `reclaim-jobs` (each reclaims the other too) mark a scheduled job (never `run-stage`/`reconcile-costs`) stuck `processing` for 60 min as failed (above the forge back-off worst case of 3 x 300 s per call, since a reclaimed job keeps running); `watch-reviews`, `watch-production`, `resume-reviews` and `watch-release` are separate tasks; `GET /api/health` is 200 while every scheduled task completed within 5 min, else 503 with the stale task slugs.

Check retries: a required check that fails on an MR head, or on a merge or release SHA a watcher waits for (staging, production, release checks), is re-run once before it counts a review round, returns the Ticket to Build or fails a release. `Forge.rerunFailed` re-runs the failed jobs of the check's workflow run (GitHub `rerun-failed-jobs`) or pipeline (GitLab retry); commit statuses and bridges cannot be re-run and behave as before. The retry is one Ticket Comment (check, run link, "retried once") and one `check_flakes` row per (Ticket, sha, check), which is also the once-only guard; while the check's workflow run still has jobs in progress (GitHub only re-runs completed runs) or the re-run is not listed yet, the Ticket stays `waiting_checks` (the 2 hour limit still applies; the production and release waits keep their 60 minute limit). Only real failures (`failure`, `timed_out`, `cancelled`) are re-run, never skipped or neutral checks. The row settles on a later gate pass: the check passed is `flake`, failed again is `failed` and behaves exactly as without retries. `products.checkRetries` is 0 or 1 (default 1; 0 turns the retry off); larger values are refused because the once-only guard makes them meaningless. Flakes of the last 30 days are listed under Factory health. Tests that pass only on Playwright's own retry never fail a check: each `e2e-fake` shard lists them in its step summary (`.github/scripts/e2e-flakes.sh`) and publishes a non-required, `neutral` check run `e2e-flaky (shard N)` whose output text is JSON `[{shard,file,title}]`; every gate pass records one `check_flakes` row per test (`checkName` `e2e: <file> › <title>`, outcome `flake`, once per Ticket and sha). GitLab has no equivalent output and records none.

Production gate: with `production_gate: human` on `release` (default; or `products.productionGate`) a Ticket accepted on staging stays open in `release` (`tickets.productionState` `awaiting_approval`) until a human approves the deploy: UI Gate "Approve production deploy" or MCP `approve_production`. The approval records a human touch `approve:production` (before the state change, so no deploy lacks an audit row), stores the merge sha it approves (`productionApprovedSha`; `watch-release` fails the deploy with a Comment if it no longer equals the Ticket's merge sha) and sets `productionState` `deploying`. A label set on the forge by anyone starts nothing. The factory deploys nothing: the Product's own pipeline reacts to the output label or to the optional `products.productionWebhookUrl` (POSTed once with `{ticket, sha, environment: "production"}`; klima-portal's manual `deploy_production` is such a pipeline). The label is delivered once per approval (`productionLabelAt` records the first successful add; it is retried only until then and never re-added when someone removes it, because every add re-triggers label-based pipelines); a failed or timed out deploy removes it. Webhook receivers must dedupe by `(ticket, sha)`: a non-2xx answer is retried on the next tick, and every POST (staging and production) carries the header `X-Bauherr-Delivery: <ticket number>-<sha>`. Label-triggered workflows run on the default branch HEAD, so with several Tickets in flight they must report their check on the Ticket's merge sha (for example by taking the sha from the Ticket page or the webhook body); a check reported on another commit is never seen and ends as `timed_out`. `watch-release` observes `products.productionChecks` (required, comma-separated) on the merge commit, counting only runs that started at or after the approval minus 60 s of clock skew: all `success` is `deployed` (stage `done`, Ticket closed `completed`); a finished check with any other conclusion is `failed`, a skipped or neutral one with the reason "deploy check skipped" in the Comment (nothing was deployed); nothing after 60 minutes is `timed_out`. One `<!-- bauherr:production -->` Comment holds result, sha, checks, approver and time. `failed` and `timed_out` are the needs-you value "Production deploy failed"; the Ticket stays open and a retry is a new explicit approval. GitLab pipelines follow with #119. Bauherr's own Product: `.github/workflows/production.yml` builds `ghcr.io/getbauherr/bauherr:edge` from the approved sha and reports the check `production` (`productionChecks = production`; `pnpm seed` sets it).

Release: when Tickets are approved for production (`productionApprovedSha` set, `deploying` or `deployed`), the scheduled task `publish-release` (every minute; also queued by the approval) publishes one forge Release per Product for the newest (by commit date) approved merge sha. Idempotency: the release body carries `<!-- bauherr:release:<sha> -->`, and the release that shipped the sha (first release whose tag commit is the sha or a descendant, so a `chore(release)` commit after the merge still matches; `findRelease`) is looked up before one is created, so a retry or a second tick never makes a second one. The body lists the batch (approved, no `releasePublishedAt`) grouped Features / Fixes (Ticket label `bug` or a `fix:` title is a fix) from the "What you get" part of the staging summaries, with Ticket and MR links; one cheap-tier model pass through the Workspace gateway rewrites it in plain language, and any error, budget block or lost link publishes the deterministic text instead. `products.releaseMode`: `notes-only` (default) never creates a tag: if the Product's tooling made a release for the sha, the notes are appended under `## What's new`; none after 6 hours posts the notes and "no release found" as Ticket Comments. `factory` tags `v<semver>` (conventional commits since the last release, first `0.1.0`), creates the Release and opens a `CHANGELOG.md` MR from `bauherr/release-v<semver>` (prepended after `## Unreleased`; a human merges, never auto-merged). Each Ticket gets `releaseUrl` and one Comment linking the release. `products.releasePrerelease` (factory mode): the tag is a pre-release `v<next stable>-rc.<n>` (n = 1 + the highest existing rc tag of that version, read with `listTags`, since a tag may exist without a release; `latestRelease` stays stable-only), the release is flagged pre-release and no CHANGELOG MR is opened. With `products.releaseChecks` (comma-separated, Bauherr: `image, npm`, the jobs of `release.yml` triggered by the tag) the Tickets get `releaseTag`, `releaseSha`, `releaseChecksState` `waiting` and no Comment yet; the same task reads those checks on the tagged sha (runs started at or after the release minus 60 s): all `success` is `passed` with the Comment "Released in"; a finished red one, or nothing after 60 minutes, is `failed` (needs-you "Release failed" with the run link, shown even on the closed Ticket; one Comment) and a re-run that turns green still ends `passed`. The npm package is staged with tag `next`; promoting it stays a human step on npmjs.com. The task only looks at Products with due Tickets: while `notes-only` waits for the release it looks again every 10 minutes; a failure is stored on the Ticket (`releaseError`, `releaseAttempts`), retried after 1 hour, and the 3rd gives up with a Comment. The rewritten notes are cached on the Tickets (`releaseNotes`) before the publish step, so a retry does not run the model again.

Everything else is automated. The `checks` gate is the Product's **scorecard** (ordered rules with a guide each: build, tests, lint baseline, pack lint, security context, evidence section — decision #38): a failing blocking rule prevents Review, re-wakes the Build Run once, then `needs_human`. Bauherr mirrors both approvals into Run state for audit. Per-type autopilot: not in v0.1.

## 3. Triggers
Only on factory-derived events (diffs of poll summaries against the stored Ticket pointer):
- entered-stage (Label change), label added (`bauherr:go`), manual (admin button sets the Label), schedule (creates a Ticket first)
- `check_failed`: CI failure on a Build Run's MR; `mr_comment`: review comment on it. Each re-wakes the Build Run within its remaining budget. A second CI failure after a re-wake → `needs_human`. In `review` these are handled by the merge gate and the round cap above.
- **Review only green heads**: `request_review` (and `finish_run` with an MR) first asks `checksGate` (`lib/actions.ts`, the same function as the merge gate: required checks of the MR head, #291's retry applied, no checks count as green once the head is 10 minutes old). Green: into Review. Pending: the Ticket stays in Build with `waitingFor: checks` ("Waiting for checks", no Run, no Review WIP slot) and the per-minute `watch-reviews` task moves it to Review when the checks are green; after 2 hours the latest Build Run goes `needs_human` with the reason. Red: `request_review` answers `{refused, checks}` and `finish_run` is refused, the session keeps its Run and fixes the head; a Ticket that was waiting for checks goes back to Build with the failing check names (no review round). Every other way into Review (the autonomous Runner's stage label, the poller, a Ticket released from a full Review column) ends in `startReviewIfReady`, which asks the same gate when no review is running: a pending head parks the Ticket in Build waiting for checks, a red head returns it to Build with the names (`parkForChecks`). A review already running is not interrupted.
- Review: entering `review` with an open factory MR (poller, `request_review`, or a Build Run finishing with an MR) starts the Review Run; returning from review starts a Build Run on the same branch.

A Run starts when a Ticket enters a stage with an agent and has no human assignee (logins the factory added for a gate do not count; a Ticket without any Run of that stage is also started once the assignee is gone). One Run per (Ticket, stage entry), unless the column is full (WIP limits below) or an earlier Ticket overlaps (Build hold below). Every start path respects `blockedBy`: the stage-entry start in `poll-tickets` uses the same open-blocker check (`hasOpenBlocker`) as `startMissingRuns`.

**Build hold** (`lib/overlap.ts`, owner decision on #270). A Build Run does not start while a Ticket of the same Product that sorts earlier in `executionOrder` (in Build or Review, open, a Ticket in Review always precedes a Build) has paths that intersect the later Ticket's. Only a Ticket with work in flight holds: a live Run (`queued`, `awaiting_session`, `running`) or an open PR; a Ticket whose latest Run is `needs_human`, `failed` or `cancelled` holds nothing, and a `type:bug` Ticket is not held by a feature that has not started (no running Run, no PR). A Ticket's paths are its linked PR's actual files (`listPullRequestFiles`) when it has one, else the `## Files` of its latest plan Comment, else none: a plan without `## Files` holds nothing until its PR exists. Two paths or globs intersect when equal, when a glob matches the other path, or (two globs) when they share a literal prefix up to the first wildcard. The later Ticket stays in Plan with `waitingFor = build` and `waitingReason = "overlaps #N"` (the chip and the Ticket-page notice read "Waiting: overlaps #N" through `waitingText`) and no Run; `enterStage('build')` does the check on entry and `pullWaiting` re-checks it on every poll, releasing the Ticket once the other is merged or no longer intersects. It also covers a Build-stage Ticket that never had a Run (`startMissingRuns`, gate assignment). Returns to Build (request changes, review changes) are never held. A held Ticket does not occupy a Build slot. `products.overlapIgnore` (glob list, Settings > Factory > Workflow, Admin only) names paths that never hold anything; the factory suggests entries (`suggestOverlapIgnore`: files changed in at least 25% of the last 100 merged PRs, `listMergedPullRequests`), a person adds them, nothing is applied automatically. Out of scope: line-level or semantic conflicts, Plan holds, Tickets of other Products.

**WIP limits** (the `wip` of a step, set in the workflow editor (`workspaces.wipLimits` is the legacy override: the editor folds it into the file and the first apply clears it); default Plan 3, Build 2, Review 3, Release 5, empty = no limit). A pull system: a Ticket may enter Plan, Build or Review only while the column has room (`lib/wip.ts` `enterStage`, under a per-(Workspace, stage) advisory lock); otherwise it stays, ready, in the column to its left (still counting there) with `tickets.waitingFor` set and no Run; only a Ticket waiting to enter a column is not counted in it. Every poll runs `pullWaiting` right to left (Review, Build, Plan), best owner rank first, so a freed slot or a raised limit takes effect on the next poll. Work already in a column always finishes: merges, the release watcher, staging acceptance, production and returns to an earlier stage are never held (a return may exceed a limit); a full Release holds new Review entries upstream. Sub-tickets count, parents (stage `parent`) do not; sub-tickets created into a full column wait. `claim_next` and the frontier work right to left: Release, Review, Build, Plan, Triage, then the owner's rank (byte order everywhere, same on the Board); `claim_run` accepts only the Run `claim_next` would return (an owner reorders by rank on the Board, not by assigning), and refuses a Run outside the frontier; its check is workspace-wide while `claim_next {product}` is product-scoped; `claim_next` moves past a Run whose claim errors (reported in `skipped`), and `claim_run` ignores such a Run for 5 minutes; parents are never claimable. Claim results list `skipped` Tickets ahead with the reason. A session may pass a stable `session` label (max 64 chars) to `claim_next`, `claim_run` and `list_frontier`; it is stored on the claimed Run (`runs.sessionLabel`), and a Review Run whose Ticket's latest Build Run has the same non-empty label is skipped as "your own build" (`claim_run` names the next Run the caller may take instead); sessions without a label are never skipped. A session that works only some stages passes `stages` (for example `["build"]`) to the same three tools: the pull order then applies within those stages only, so an unclaimed Review above does not hold a Build session back; `claim_run` refuses a Run outside them, an unknown stage is an error, and an empty or missing `stages` means all. `poll-tickets` syncs `tickets.blockedBy` from the forge (native dependencies and `Blocked by: #N` body lines, which already include the plan `after:` edges) for every Ticket it saw change: the forge is the truth, so added and dropped dependencies take effect within a poll; a blocker without a local Ticket in the Product is ignored until it is polled, and a forge read error keeps the stored set. Autonomous Runs execute in parallel, at most `BAUHERR_MAX_RUNS` (default 4) per worker process; the WIP limits bound Tickets, not Runs.

**Expedite lane** (label `bauherr:expedite`, `tickets.expedite`, synced by `poll-tickets`). A human sets the label or presses Expedite on the Ticket page (`expedite` in `src/lib/actions.ts`); Triage only proposes it (`expedite: true` in the triage output puts `bauherr:expedite-proposed` on the Ticket, which reads as the needs-you "Expedite?" and is never applied by itself). An expedite Ticket without a stage skips Triage: `startExpedites` (every poll) moves it to `plan`, or straight to `build` when its body has a `## Plan` or `## Steps` section (`lib/expedite.ts`). Bypasses: it enters Plan, Build and Review whatever the WIP limits say and is not counted against them (one extra slot per column); the overlap hold never holds it, while later overlapping Tickets wait for it; the plan gate is off for it (`advancePlan` accepts the plan, the plan is posted for audit). Human gates after Build are unchanged. One expedite Ticket per Workspace is in flight (Plan to Release, until done); a second stays without a stage, first come first served, with a Ticket Comment, and enters when the first is done. Settings > Factory > Workflow "Expedite lane" (`workspaces.expediteLane`, default on): off ignores the label (`tickets.expedite` stays false) with a Ticket Comment. Removing the label returns the Ticket to the normal flow on the next poll. The `plan/hotfix` template (`pack/skills/plan/hotfix.md`) is the short plan for it. Pull order: `claim_next`, `list_frontier` and `claim_run` put the Ticket the lane serves (`isExpediting`) before every other, right to left among themselves; lease, blocked and own-build rules still apply. The `heartbeat` answer carries `expedite: {ticket, run}` while such a Run is unclaimed. Gate notice: a gate on an expedite Ticket is notified in the same pass the Ticket reached it (the release and review watchers call `syncGates` for expedite Tickets right after their sweep; the minute sweep handles expedite Tickets first; the Comment is claimed by one conditional UPDATE of `tickets.gateNoticeClaim`, so parallel passes post it once, and a forge error releases the claim), and the Comment reads `@owner: Hotfix, <gate> — <link>`. Skipping staging is a human decision per Product: `products.expediteSkipStaging` (Product page, default off, shown while the workflow has the staging gate). With it on, an expedite Ticket whose merge is on staging passes the Accept-on-staging gate by itself (`passStaging`, recording a `auto:staging:expedite-skip` touch that names the setting and who enabled it and when: `products.expediteSkipStagingBy/At`, written by `saveDeploy` when the toggle flips) and opens the production gate at once; the production approval always stays human, and the factory never skips a gate for a Product that did not opt in. Lead time: `tickets.expediteAt` is set when the flag first appears; Factory health shows the mean of `releaseAt - expediteAt` of the last 5 merged Hotfixes. Board: see `docs/ui.md`.

## 5. Run states and retries
`queued → running → succeeded | failed | cancelled | needs_human | budget_exhausted | abandoned`.
- Ticket lease: a session Run is leased to one coordinator by a `leaseToken` (only its hash is stored) returned by `claim_run` and required on every owning call, so a second session under the same user is refused. The lease applies to claimed Runs and lasts 30 minutes from the last sign of life: any call with a valid `leaseToken` renews it (every lease-checked tool response carries `leaseExpiresAt`), and so does a push to the Run's branch (`bauherr/<ticket>-<run>`, else the head of the MR the Run carries): `expire-sessions` compares the head SHA (one `getBranch` request) with `runs.last_seen_sha` for a Build Run whose last sign of life is 20 minutes old and renews when it moved; an expired lease is never revived by a push, and a forge error skips the check. A wrong token or an already lost lease never renews. Unclaimed session Runs do not expire (only unclaimed Triage Runs do). On expiry the Run ends `abandoned` with the error `session lease expired (last sign of life <iso>, last call <tool>)` and a new `awaiting_session` Run (same Ticket and stage, `previousRun` set) is claimable; a second consecutive `abandoned` Run ends `needs_human`. A Workspace Bauherr can "Release lock" on the Run page (same as expiry, never `needs_human`; recorded as a human touch). A late owner gets `lease lost`. `abandoned` is terminal and not rerunnable: its successor Run exists. See [run-contract](../../pack/skills/run-contract/SKILL.md).
- One automatic retry on the `strong` tier; a second failure → investigation, then the owner (escalation ladder below).
- `cancelled` when the Ticket is closed, moved back, or a human claims it.
- `budget_exhausted`: the gateway answered 429 because the Workspace budget is used up. Terminal, no retry.
- Concurrency key `ticket:<id>`; `retries: 0` at job level (retry is Bauherr's).

### Liveness

Invariant: every open, non-parent Ticket in plan, build or review has a live Run (`queued`, `awaiting_session`, `running`), a visible wait (`waitingFor`, `blockedBy`, a human gate) or a needs-you with a reason and one primary action. `deadTickets` (`lib/liveness.ts`) lists the Tickets without a live Run or wait, each with a cause:

| Cause | Meaning | Repair (task `watch-liveness`, every 5 minutes) |
|---|---|---|
| `mr-missing` | review, the linked MR is closed or none is linked | an open factory MR on `bauherr/<number>-*` is linked to the newest Build Run and the review resumes; none: back to Build with the note to open a new MR |
| `checks-red` | review escalated, MR open, a finished check failed | back to Build on the same MR, failing checks as Current instructions (no round counted) |
| `run-failed`, `run-abandoned`, `run-stuck` | latest Run of the stage failed, was abandoned, or ended `needs_human` with `reasonKind` `stuck` | the escalation ladder (below): one strong successor Run; a stopped strong Build starts an investigation; anything else stays a need (`Run failed`) |
| `run-cancelled` | latest Run of the stage was cancelled | none: need `Cancelled` (Re-run, Back to backlog) |
| `review-escalated` | review `needs_human`, MR open, checks not red | at the round cap: one more fix round with Build and Review on `strong`, then the owner. Below the cap: none, need `Needs you` (Back to build) |
| `review-invalid` | review `ready_for_human` because the review output was invalid (`problem`) | one successor review on `strong` (`reviewState` reset); a second invalid output stays with the owner |
| `review-stalled` | review `ready_for_human` (no `problem`) for over 30 minutes, `reviewWaitingSince` set when the Ticket was parked, with no human touch since | none: shown under Factory health as "Waiting for a human merge for over 30 min" |
| `triage-expired` | untriaged, marked covered, its only Triage Run ended `abandoned` | `triagedAt` and `triageAttempts` reset, so the next poll offers Triage again |

**Escalation ladder** (`lib/escalation.ts`, #378): a stuck Ticket climbs four rungs by itself and reaches the owner only at the last. 1. The stage's normal Run. 2. One retry on `strong` with doubled caps (`runs.escalation = { step: 2, reason, previousRuns }`, written with the Run create; also the successor of an abandoned session Run and the extra fix round at the review round cap, where the following review is strong too). 3. An investigation (below; Build only). 4. The owner: the failed Run gets `reasonKind` `decision` (or `access` when the budget is out) and only then shows `Run failed` with Re-run; until then the card says Escalated and the Ticket page lists the steps. `needs_human` carries a `reasonKind` (`finish_run`, or `kind` per blocked Goal statement in `goal.json`): `decision` and `access` reach the owner, `stuck` enters the ladder, a missing one is `decision`. Session claim payloads carry `run.tier: 'strong'` and `run.escalation`. Budget guard: before an escalated autonomous Run the USD budget (`budgetUsd30d`, gateway spend) is checked; when spent the ladder ends at the owner with "budget" (token budgets and session Runs are not checked: there is no spend source). Every step is one line in the Ticket's `<!-- bauherr:escalation -->` Comment (keyed by the stopped Run, written before the Run so a retry never doubles it): step, stopped Run with cost and reason, tier, model, caps.

**Investigation** (`lib/investigation.ts`): a second Build failure moves the Ticket to Plan (`waitingReason` "failed twice: investigate", it leaves the Build slot; Plan WIP does not hold it back) and starts one Plan Run with `runs.investigation = { failedRuns, stage }`. That Run, and the one fresh Build Run after an investigation, are escalated (owner addition): tier `strong` (session claim payload `run.tier: 'strong'`), investigation Plan Run 60 turns and $2, the Build Run twice the normal turns and budget. The Run reads both failures in the Ticket's `<!-- bauherr:investigation -->` Comment (shown under Investigation on the Ticket page; the Board card says Investigating) and ends with MCP `submit_investigation` (autonomous: `.bauherr/investigation.json`): `revise` (plan approval withdrawn, a revised plan follows through the plan gate), `fix-ticket` (a `type:bug` Ticket is filed and set `blocked-by`; the Ticket waits for Build and `pullWaiting` starts a fresh Build Run once the fix is closed, its failure counts as a first failure) or `needs-human` (the Run ends `needs_human` with the question). The Comment names tier, model and cost of each escalated Run. A Ticket gets `MAX_INVESTIGATIONS` (2); after that the second failure stays with the owner.

**MR resolution** (`prOf`): the newest Build Run's `artifacts.prUrl`; when that MR was closed unmerged (or a review/release Ticket has none), the newest open factory MR of the Ticket (head `bauherr/<number>-*`) stands in, with no DB edit. A hand-made replacement can be linked with the MCP tool `relink_mr {runId, leaseToken, prUrl}` (Build Runs). **Stacked MRs**: `mergePullRequest` with `deleteBranch` first retargets every open MR whose base is the merged head branch onto the merged MR's base; if that fails, the branch is kept and the failure is reported as `branchDeleteError`.

Review restart (task `resume-reviews`, every minute): a Ticket parked at `ready_for_human`, or at `needs_human` below the round cap, whose MR head differs from the last review's `reviewedSha` is cleared (conditional UPDATE) and reviewed again, unless `rebindReview` moves the verdict (same-diff main merge); one Comment `New head <sha7>; review restarted (was <state>).`

Every sweep also stores its findings for the pages: `tickets.liveness` = `{cause, need, at}` for each Ticket still dead after the repairs, cleared for every other Ticket. Factory health reads these (no forge call); a finding older than 15 minutes shows as "could not be checked". `deadTickets` and `invisibleDead` stay for jobs and MCP tools.

Each repair posts one Comment line with the marker `<!-- bauherr:liveness:<cause>:<run id> -->`, which makes it once per (Ticket, cause, Run). An unclaimed Triage Run no longer expires: it waits for a session like any other unclaimed Run (an expiry used up the Ticket's triage attempts). MCP `return_to_build` lets an agent do the `mr-missing` and `checks-red` repairs itself; it is refused for a Ticket that is not dead for one of those causes. Gates stay human-only.

## 6. Human takeover
A human assignee or a manual Label move cancels the active Run. Nothing restarts until `bauherr:go` or unassign. The next Run reconciles the worklog ([worklog](../../pack/skills/worklog/SKILL.md)).

## 7. Human interaction
One decision sheet per Ticket per gate (the newest plan or triage Comment; only answers posted after it count, so a new sheet starts unanswered), with recommended defaults and a `critical` flag; at most one human touch. With the plan gate off, an unanswered critical decision on a posted plan reopens the refine hold (stage label removed, `bauherr:needs-refinement`, one Comment): answering it re-plans and the Ticket then proceeds without approval. Protocol: [decision-sheet](../../pack/skills/decision-sheet/SKILL.md).

Templates: every text written for people has a template in `pack/templates/` (`request`, `plan`, `decision`, `review`, `staging-summary`, `release-note`, `worklog`, `triage-questions`, `progress`) that a Workspace can override in Settings > Templates (table `templates`, one row per Workspace and name). The factory renders the staging summary, release notes, request issue body, triage sheet, worklog start and the decision Comment from the Workspace's template (`template()`, `renderTemplate()`); a default template produces exactly the text the factory wrote before. Agents get the same structure: `load_skill` appends the templates of the skill (`SKILL_TEMPLATES`: run-contract gets plan and worklog, review gets review, triage gets triage-questions, intake gets request) under `## Template: <title>`, and the autonomous Runner gets them in the run context (`RunCtx.templates`) and appends them to the materialised skills. The plan's TL;DR is located by the Workspace template's current heading text (default `TL;DR`).

## 8. Roles and agent sessions
Roles come from `team.roles` of the factory file and are the only source of roles: a session never assigns itself a role. Policy: [team-policy](../../pack/rules/team-policy.md).

**Agent session** (`agent_sessions`): a connected client (e.g. Claude Code) working as one role. `connect` registers it (`publicId` `ses_...`, role, `clientKey`, client, reported model; the same `clientKey` of an owner in a Workspace revives the row), `next_work` pulls the next Run of a stage whose `role` is the session's through the `claim_next` path (stage mode, WIP and the `agents` cap of the role respected; at the cap or with nothing queued it answers a plain reason), every agent tool takes an optional `sessionId`, `disconnect` ends it and releases its Runs. Without `sessionId` the legacy claim and its 30-minute lease are unchanged. A Run claimed by a session carries `runs.session`, `role`, `model`, `provider`, `clientName`, `clientVersion` and `executor: session`; the history event's actor is `<label> (<role>)`.

**Presence**: each call writes `lastSeenAt` (at most every 15 s). A span is the time a session holds a Run: one `session_spans` row per (session, Run), opened at the claim and extended by every call for the Run, forced at finish, release and disconnect; a Run that loses its lease keeps its last signal. Active time = sum of span durations. A session with no running Run and silent for `BAUHERR_SESSION_TIMEOUT_S` (default 600) is ended (`endReason: timeout`) by the sweep in the liveness task (every 5 minutes). `loadTeam(payload, workspace)` reads roles, sessions (`working` = a running Run, `idle` = seen within the timeout, `offline` = disconnected, kept 24 h) and the autonomous Runs per role from the database only.

**Exceptions role**: the one role with `exceptions: true`. When nothing normal is claimable for it, `next_work` returns the next stuck Ticket as `{exception: {ticket, problem, since, allowed}}` from the findings the liveness sweep stores in `tickets.liveness` (database only, findings older than 15 minutes ignored; `since` is the Ticket's last update); `allowed` is what an agent may do today (`return_to_build` for `mr-missing` and `checks-red`), never a human gate tool, and empty for causes the owner decides or the factory repairs itself.

## 10. Budgets
- Per Run: `maxTurns` and `maxBudgetUsd` set by the Runner; the real cap is the gateway key budget (`maxBudgetUsd` can overshoot).
- The gateway enforces the Workspace budget (USD, rolling 30 days); exhaustion ends the Run `budget_exhausted`.
- Re-wakes draw from the same Run budget.
- At 80% the Run converges or declares a blocker.
- Defaults are config values per stage, not fixed here.

## 11. Egress and security context
- Code and context leave only via the gateway: [egress](../../pack/rules/egress.md), [egress-guard](../../pack/hooks/egress-guard.sh).
- The gateway is part of the instance, and the Workspace's provider credential never reaches an agent. Operator notes: [legal](../legal.md).
- Each Product keeps a `SECURITY-CONTEXT.md` at `products/<slug>/` in the Knowledge repo; the `scan` stage of `pack/workflow-security.yaml` reads it: [security-context](../../pack/rules/security-context.md).
- The `distill` stage is a job-driven Run (no agent session) queued when a review merges a Ticket that went back to Build or that a later fix names. It proposes one skill as a Knowledge-repo PR on `bauherr/<run-id>`, replayed against its own eval cases (baseline without the skill must fail, with it >= 0.9, per case >= 0.8). Caps: 1 extraction call (60 KB in, 2k out), 20 eval calls per suite, $1 per distillation, 5 per Workspace per day. The factory never merges the PR; `skill_proposals` holds its status. Approval is a human gate like `approve`: `approveSkillProposal` (Admin only; MCP tool `approve_skill_proposal` is `access: 'human'`, so an agent key is refused) merges the PR with `expectSha` (the head the owner saw; a moved head is refused, nothing merges), records an `approve:skill` human touch and sets the status to `accepted`. Only `proposed` or `replayed` proposals can be approved. `watchKnowledgePrs` stays limited to `bauherr/edit-*` and never touches these PRs.

## 13. What a Product user sees
Intake session, then the Ticket in the Ticket source with its Stage Label and Comments (plan, review, decision sheets addressed to them). No Runs, worklogs, budgets or configuration.

Intake: `POST /intake/api/sessions` (Product), `.../:id/messages` (one interview turn, SSE `turn` event), `.../:id/submit`, `GET .../:id` (resume: status, messages, draft, split, last turn). The engine asks one question per turn through the gateway (skill [intake](../../pack/skills/intake/SKILL.md), standard tier), at most 6 questions; completeness (problem, context, >= 2 criteria, screenshot for screen requests) is computed by the engine, not the model. Submit creates the Ticket without a stage label, so Triage picks it up, with `type:`/`product:` labels, an `## Open` section for gaps and the interview as a Comment. A request with several independent problems gets a `split` (2 to 6 drafts, each checked on its own); the requester confirms the count and submit (`{ expect: N }`, refused with 409 when N differs) creates one Ticket per item (marker `session=<id> part=<i>`, so a retry never duplicates) with the interview, the screenshots and an `intake-siblings` Comment listing the others. The New request page lists the requester's open sessions and resumes the latest; the unsent text is kept in the browser.

Persona `owner`: the question card in the Ticket's docked chat thread starts it while the decision sheet has open rows ("Answer N question(s)" in the action bar, and the Inbox card open the dock on it), an `intake_sessions` row with persona `owner` and `draft.ticket`. The engine's `ownerQueue` asks the sheet's unanswered rows one per turn, critical first, the sheet default marked recommended. A click on a listed option is recorded without a model call; free text and the "Why does this matter?" chip use one cheap-tier model call that either explains (records nothing; the chat then offers "Use my text as the answer", which records the typed text without the model) or lets the text through as the answer. Each answer goes through `postDecisions` (the same `<!-- bauherr:decisions -->` Comment and worklog Decisions as the MCP tools); the session ends `submitted` when no row is left and the card closes with a summary read from the state after the last write.

## 14. Pack artifacts index
Manifest: [pack.yaml](../../pack/pack.yaml). Hooks map to SDK events in [hooks.yaml](../../pack/hooks/hooks.yaml).

### `factory.yaml` (the file)
The factory file declares the team and the workflow of a Workspace. `pack/factory.yaml` is the shipped default; every Workspace can run its own (see "Apply, versions, export" below). All stage lists in the code (Board columns, pull order, WIP stages, repairable stages, ...) are derived from the Workspace's workflow by `apps/server/src/lib/workflow.ts` (pure: `parseFactory`, `lint`, `compile`, derived lists such as `board()`, `pullRank()`, `gates()`, `graph()`); code gets the workflow with `workflowFor(workspace)` (`lib/factory.ts`).

#### Schema
```yaml
version: 1
team:
  roles: {<id>: {title, tier | (provider and model), agents?, avatar?, skills?, exceptions?, profile?, profile_file?}}
workflow:
  stages:
    - {name, kind, title?, role?, skill?, mode?, gate?, production_gate?, wip?, exclude_labels?, outcomes: {<outcome>: <stage | escalate | backlog>}}
  migrate: {<old stage>: <stage>}   # optional, see apply
  aliases: {<old stage>: <stage>}   # optional, accumulated by apply
```
Names match `^[a-z][a-z0-9-]*$`, are unique and not `checks`, `scan`, `distill`, `escalate`, `backlog`; `title` defaults to the name. A role has a `title` and exactly one of `tier` (one of the Workspace's tiers) or `provider` (the slug of an LLM Connection of the Workspace) plus `model`; `profile` is its text (`profile_file` is a path inside the pack dir, inlined on apply); `agents` is a positive integer (the most session Runs the role works at once); `avatar` is a free id the UI maps to a picture (default: the role id); `skills` is a list of 1 to 6 short labels (at most 24 characters each) shown on the Team page and returned by `connect` and `loadTeam` (default none); `exceptions: true` marks the one role that also receives stuck Tickets (see Roles and agent sessions). The model of every Run is its stage role's: `tier`, or the pinned `provider` and `model` (written to `runs.model` and `runs.provider`; escalated Runs use `strong`). Roles no stage names are allowed (available for custom stages). The default file ships `orchestrator` (exceptions), `engineer`, `reviewer` and the specialists `security`, `ux`, `test`.

#### Stage kinds
Built-in behaviour binds to a stage's kind, never to its name: names are free (`name`, `title`, `outcomes` targets, WIP keys, `bauherr:stage:<name>` labels), so a file that renames every stage works unchanged (`tests/renamed-flow.test.ts`). Code tests a Ticket stage with `is(wf, stage, kind)`, a Run with `kindOfRun(wf, run)` (`runs.kind`), and writes a stage with `nameOf(wf, kind)`. No other code lists or compares stage names (`tests/stage-lists-guard.test.ts`, `tests/stage-names-guard.test.ts`, `tests/default-workflow-guard.test.ts`).

| Kind | Outcomes (exactly) | Role | What it does |
|---|---|---|---|
| `triage` | `plan, refine, skip` | required | Triage Run on untriaged Tickets; `refine` holds for the owner's answers |
| `plan` | `done, decisions` (+ `split`) | required | Plan Run; `gate: human` (Approve plan, on in the shipped file) |
| `container` | `children_done` | none | parent of split sub-tickets, no Runs |
| `build` | `done, stuck, replan` | required | Build Run, MR with Evidence; `done` = request review, `replan` is reported with `finish_run outcome: replan` (session) or `.bauherr/outcome.json {outcome: replan, comment}` (autonomous) |
| `review` | `clean, changes, stop` | required | Review Run, merge gate; `changes` returns to build, `clean` merges and enters release |
| `release` | `accepted, changes` | none | staging, `gate: human`, `production_gate: human`, deploy watchers |
| `done` | none | none | closed |
| `agent` | at least one | required, plus `skill` | a role works the Ticket with the skill and reports an outcome (below) |
| `human` | 1 to 4 keys `^[a-z][a-z0-9_-]*$` | none | the Ticket waits for a person (below) |

`agent`: a Run of kind `agent` in the stage (session or autonomous, by the stage's mode as any Run). It may read the Ticket, the plan, the worklog and the open MR and post one comment; it cannot push, open or merge an MR, create sub-tickets or touch approval labels (the session has no tools for them, the Runner is read-only without push credentials). It reports an outcome of the stage (session: `finish_run outcome comment`; autonomous: `.bauherr/outcome.json {outcome, comment}`); a missing or invalid outcome fails the Run. The comment carries the marker `<!-- bauherr:stage:<name> -->`. WIP applies as for the built-in columns.
`human`: no Run. The Ticket shows the need "Decision needed" (phase `human`), the Ticket page's action bar has one button per outcome key (the stage `title` is the heading) and `decide {ticket, outcome, note?}` (MCP, human key only) does the same; both record a human touch `decide:<stage>:<outcome>`.

#### Outcomes and routing
`advance(payload, ts, ticket, outcome, {by, run?})` (`lib/advance.ts`) takes a Ticket out of its stage: it looks up `outcomes[outcome]` and enters the target by the TARGET's kind: `escalate` is the escalation ladder of the finished Run; `backlog` the untriaged state; `plan` and `build` (from upstream) a WIP-ruled move; `build` from a later stage a hand-back (same MR, the note goes into the worklog, no review round); `review` the WIP-ruled entry plus the Review Run; `agent` a WIP-ruled move plus its Run; `human` a move without a Run. `release` and `done` are entered only by the review and release logic. An outcome with no mapping ends the Run as `needs_human` (decision). Routed through `advance`: triage `plan`, plan `done`, build `done` (request review, checks watcher) and `replan`, review `stop`, and every `agent` and `human` outcome. Built-in and fixed by lint: `review.changes` and `release.changes` to build, `review.clean` to release, `release.accepted` to done; the plan `decisions`/`split`, triage `refine`/`skip`, `build.stuck` use their built-in code.

#### Lint
`lint()` (run by `compile()` and `applyFactory`): (1) `version` is 1; names as above; (2) one `triage` first, one `done` last, at most one each of plan, container, build, review, release, and a container iff `plan` has a `split` outcome; (3) build, review, release all present or all absent, with `review.changes` and `release.changes` to build, `review.clean` to release, `release.accepted` to done; the review stage is reachable from `build.outcomes.done` passing only through `agent`/`human` stages, and no stage but the review stage targets the release stage; (4) the outcome keys above (`agent` at least one; `human` 1 to 4 keys of the pattern); (5) every target is a stage, `escalate` or `backlog`, every stage is reachable from triage and reaches done; (6) `role` required on triage, plan, build, review, agent (plus `skill` on agent), forbidden on container, release, done, human, and a key of `team.roles`; a role has a `title` and one of `tier` or `provider` plus `model` (never one of `provider`/`model` alone, never with `tier`), a positive `agents`, a non-empty `avatar`, 1 to 6 `skills` of at most 24 characters, a boolean `exceptions`, and at most one role has `exceptions: true`; (7) `gate` only on plan and release, `production_gate` only on release, `wip` a positive integer on plan, build, review, release, agent, human, `mode` `session` or `autonomous`; (8) `migrate` and `aliases` map non-current names to current stages.

#### Apply, versions, export
Each Workspace runs its own workflow: `workspaces.workflowVersion` points at the active `workflow_versions` row (`version` per Workspace, `source` = the YAML with every `profile_file` inlined as `profile`, `compiled` = the `Workflow`, `hash` = sha256 of the canonical compiled JSON, `appliedBy`, `appliedVia` = `ui|api|cli|boot|seed`, `note`); no pointer = the pack default. `workflowFor(workspace)` is sync, from a process-wide map refreshed by `loadWorkflows(payload)` at most every 5 s (the app, worker and poller each keep their own copy, so a change reaches them within 5 s; `workflowFor` throws when a process never loaded it; `onInit` loads at boot, job handlers, the MCP route, `payloadClient()` of the UI and the API routes refresh). `DEFAULT()` (the pack file) is allowed only in the files listed in `tests/default-workflow-guard.test.ts`.

`applyFactory(payload, workspaceId, yaml, {by, via, note?, baseVersion?, dryRun?})` parses, inlines `profile_file` (relative to the pack dir, never outside it), lints, checks the context (every stage `skill` is `pack/skills/<name>/SKILL.md`; a role's `provider` is the slug of an LLM Connection of the Workspace; its `tier` one of the Workspace's tiers), compiles and compares the hash with the active version (equal: `changed: false`, no row). Otherwise one transaction under an advisory lock per Workspace inserts version n+1, applies `workflow.migrate`, accumulates `aliases`, clears `workspaces.wipLimits` (the file's `wip` governs again; a Workspace override saved later wins) and moves the pointer; a `baseVersion` (`If-Match`) that is no longer the active version is refused with "the workflow changed since you loaded it". `dryRun` returns the findings and what would migrate.
- `workflow.migrate: {<old stage>: <new stage>}`: a stage that disappears while it holds Tickets (any state) or active Runs needs an entry, otherwise the apply is refused with a finding. It rewrites `tickets.stage`, `waiting_for`, `factory_stage`, the stage part of `history_key` and `runs.stage` of the Workspace. Same kind: a rename, active Runs continue. Different kind: the stage's live Runs are cancelled and the normal start logic starts the new stage's Run.
- `aliases` accumulate (old name to current stage) in the compiled workflow, so `stage(wf, oldName)` and forge labels written before a rename still resolve; the poller replaces an alias stage label with the canonical one (at most 20 Tickets per tick, no "stage rejected").
- Entry points (infrastructure as code): the workflow editor `/workflow/edit` (Admin); `GET`/`PUT /api/workspaces/<slug>/factory` (body = YAML, `?dryRun=1`, `If-Match: <version>`; session or the Admin's personal API key, an agent key gets 403; 422 on findings, 409 when stale); `bauherr apply -f factory.yaml --workspace <slug> [--dry-run] [--url <instance>]` and `bauherr export --workspace <slug>` (personal key in `BAUHERR_API_KEY`; the CLI inlines `profile_file`s relative to the YAML file; exit 1 on findings); `BAUHERR_FACTORY_FILE=/path/factory.yaml` (+ `BAUHERR_FACTORY_WORKSPACE=<slug>`, default every Workspace) applied at boot, idempotent by hash, an invalid file is logged as an error and the active version stays. A UI/API/CLI apply writes a `human_touches` row `apply:factory`; boot and seed applies write none, `appliedVia` says so and the editor status line shows "from the boot file". `exportFactory` returns the active `source`, or the pack file with profiles inlined.
- Workflow editor (`/workflow/edit`): the draft is the factory file as one text. Design edits are pure text operations (`lib/workflow-edit.ts`), each result is checked with `lint` from the browser-safe `lib/workflow-rules.ts` (re-exported by `lib/workflow.ts`); positions and path targets the rules refuse are found by trying the edit. Nothing is live until Apply: Review changes lists `describeChanges(before, after)`, the server dry run (`applyFactory(..., {dryRun: true})`, which returns `held: [{stage, tickets, runs}]` for removed steps that hold work so the editor can write `workflow.migrate`), and applies with `baseVersion` (a stale base is refused and the draft kept). History lists `workflow_versions`; Restore loads a version's `source` (or the shipped file) into the draft with the note "Restore of version N" and goes through the same review. The editor's base file is the active file with `workspaces.wipLimits` folded into the steps' `wip`.
- **Presets** (`pack/presets/{solo,standard,careful}.yaml`, read by `lib/presets.ts` from the pack dir, else the core pack): factory files the setup wizard applies as a UI apply (note "Setup: <preset> team"). `solo`: one engineer role works every stage, no plan gate, production gate on. `standard`: equal to `pack/factory.yaml` (a test fails when they differ). `careful`: standard plus `gate: human` on `release` and an `agent` stage `security` (role `security`, skill `mr-security-review`) between build and review: `pass` to review, `findings` back to build. Every preset must lint clean (test).
- **Return to the plan stage**: an outcome of any later stage (a `build` replan, an `agent` or `human` stage) that targets the plan stage drops `bauherr:approved:plan`, moves the Ticket and starts a new plan Run (`advance`), so the plan is made and, with the gate on, approved again.

## 15. Steps and workflow config
A stage is an ordered DAG of steps (decision #44). Step types: `agent-run` (a Run with a Goal), `external-service` (a connected agent service, e.g. a code-security scanner; callback with poll fallback; findings become Tickets, Comments or scorecard results), `ci-job` (wait for a named check), `human-gate`, `check` (scorecard rule). Step contract: `{id, type, needs, inputs, timeout, budget?, retries}` → `{status, outputs, evidence, started, finished, cost}`. A failed blocking step stops the stage; *repair run* re-runs failed steps only.

Gate keys: `gate: human` on `plan` or `release`; any other value is ignored. The compiled version records the enabled gates (`humanGates()`) with the DAG. Where the workflow lives (decision #45): base `pack/factory.yaml` in the core pack (read-only in the UI), per-Product overlay `products/<slug>/workflow.yaml` in the Knowledge repo; the factory compiles the merged DAG into a `workflow_versions` row that Runs reference. Validated by `bauherr pack lint`.

What the Bauherr sees per Ticket run: graph (nodes with status, duration, type, resource), timeline (nested sub-steps, dependency arrows), list (filterable), run details (launched by, started, ended, duration, status, cost), repair run. Per Product: the compiled workflow with the overlay diff highlighted.

## 16. History and flow metrics
**Usage** (`usage_entries`): tokens and cost per Run and model, `source` `gateway` (reconcile, replaced on re-run), `session-reported` (cumulative `usage` of a session tool call, or the usage hook's delta; ignored for a Run the gateway priced) or `chat` (read from `chat_messages.answer`). `usage_cursors` holds the hook's cursor per (session, Claude session). See [cost.md](../cost.md).

Every change of a Ticket's `stage|phase` appends a **ticket event** (`ticket_events`, append-only): `ticket`, `at`, `stage` (the stage the Ticket is in from then on), `stageKind`, `phase`, `fromStage`, `outcome`, `run`, `executor` (`session`, `runner`, `ci`, `human`, `factory`), `actor` (person or session label), `cause` (short machine reason: `moveStage:request_review`, `run:claimed`, `run:finished`, `gate:approve:plan`, `poll`, `sweep`), `workflowVersion` (reserved) and `backfilled`. `tickets.historyKey` holds the newest `stage|phase`; `record` (`lib/history.ts`) inserts an event only when one conditional UPDATE of that key changes it, so concurrent callers write a change once, and it never throws into the caller. An event's span ends at the next event (now for the newest; a `closed` event has none). A Ticket without a stage label is in the triage stage.

Phase, first match (`phaseOf`): `closed` (Ticket closed or in the done stage); `working` (a Run of the Ticket's stage is running) or `queued` (one is queued or awaits a session); `human` (it needs the owner: `needsOf`, the gate sweep's input); `ci` (waiting for checks, the merge queue or a deploy: `waitingFor` = checks, review `waiting_checks` or `queued`, release `waiting` or production `deploying`, release checks `waiting`); else `queued`.

Hooks: `moveStage` (every factory stage move, with its `why`), the poller's Ticket upsert, the Run lifecycle (queued, claimed, finished, released, abandoned, the Runner's start and end), human gate actions (`gate:<touch kind>`, `executor: human`), release and production state changes, and the minutely gate sweep (`cause: sweep`), which repairs any hook that was missed within a minute. Migration `ticket_history` backfills Tickets from their creation, Runs and approvals (`backfilled = true`, no exact stage-entry times).

Definitions (`flow()` in `lib/history.ts`, for the Tickets whose first event is in the window): **lead time** = first event to the first `closed` event; **cycle time** = first event outside the triage stage to the first `closed` event; **time in stage** = the sum of the spans of a stage, split by phase (working / queued / human / ci), with median and p85 per stage and phase over Tickets, and throughput = Tickets reaching done per ISO week.

A Run records who ran it: `executor` (`session` or `runner`), `clientName` and `clientVersion` (the `client` argument of `claim_run` / `claim_next`, else the MCP `User-Agent`), `model` and `provider` (as the session said, or for the Runner the model the agent reported and the preset of its Connection), `role` and `outcome` (reserved). `steps.finishedAt` is set when the next Step starts or the Run ends.
